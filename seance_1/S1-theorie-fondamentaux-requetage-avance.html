🖥️N1  Explorer une base avec psql
Prise en main

🎯 À quoi ça sert

Avant d'écrire des requêtes, il faut savoir où l'on est et ce que contient la base. psql propose des méta-commandes, qui commencent par une barre oblique inversée, pour explorer la base sans écrire de SQL.

💡 Analogie — psql est la télécommande de PostgreSQL : les requêtes SQL choisissent le programme, les méta-commandes naviguent dans les menus.

🧩 Syntaxe

psql
\l              -- lister les bases de données
\c cours_sql    -- se connecter à une base
\dt             -- lister les tables de la base courante
\d joueurs      -- décrire une table : colonnes, types, contraintes
\x              -- basculer en affichage vertical (lignes très longues)
\q              -- quitter

Les méta-commandes n'ont pas de point-virgule. Les requêtes SQL, elles, se terminent toujours par ;.

🔬 Exemple commenté

Vérifier la base et l'utilisateur courants avec une vraie requête SQL :

SQL
SELECT current_database() AS base, current_user AS utilisateur;
▶ Résultat 1 ligne
baseutilisateur
cours_sqlpostgres

Puis \d joueurs affiche la structure complète de la table : colonnes, types, valeurs par défaut, clé primaire, contrainte CHECK sur les buts et clé étrangère vers equipes. C'est le premier réflexe face à une base inconnue.

⚠️ Piège fréquent

Oublier le ; : l'invite passe de cours_sql=# à cours_sql-# et psql attend la suite. Tapez ; puis Entrée, ou Ctrl+C pour annuler.
🏗️N2  Créer une table : types et contraintes
Structure

🎯 À quoi ça sert

Une table décrit la forme des données. Les types disent ce qu'une colonne peut contenir, et les contraintes refusent les données incohérentes avant même qu'elles n'entrent dans la base.

💡 Analogie — une table, c'est un tableur très strict. Les contraintes sont le videur à l'entrée : un prix négatif ou une ligne sans titre ne rentre pas.

🧩 Syntaxe

TypePour stockerExemple
INTEGERNombres entiersbuts, quantité
NUMERIC(p,s)Décimaux exacts : l'argent59.90
VARCHAR(n) / TEXTTexte limité à n caractères / texte librenom, description
BOOLEANVrai / fauxdisponible
DATE / TIMESTAMPTZDate / date + heure avec fuseaudate de sortie, horodatage
INTEGER GENERATED … AS IDENTITYIdentifiant auto-incrémenté (norme SQL)id
SQL
CREATE TABLE nom_table (
    colonne  TYPE  [contraintes],
    ...
);
-- Contraintes : PRIMARY KEY, NOT NULL, UNIQUE, CHECK (condition),
--               DEFAULT valeur, REFERENCES autre_table(colonne)

🔬 Exemple commenté

SQL
CREATE TABLE test_types (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- id automatique
    titre       VARCHAR(100) NOT NULL,                            -- obligatoire
    prix        NUMERIC(6,2) CHECK (prix >= 0),                   -- jamais négatif
    disponible  BOOLEAN      DEFAULT true,                        -- valeur par défaut
    sortie      DATE,
    cree_le     TIMESTAMPTZ  DEFAULT now()                        -- horodatage auto
);

INSERT INTO test_types (titre, prix, sortie)
VALUES ('Manette sans fil', 59.90, '2026-03-15');   -- id, disponible, cree_le : automatiques

SELECT id, titre, prix, disponible, sortie FROM test_types;

DROP TABLE test_types;   -- on supprime la table de test

t signifie true : la valeur par défaut a été appliquée.

⚠️ Piège fréquent

Utiliser FLOAT ou REAL pour de l'argent : ces types sont approximatifs et produisent des arrondis faux (0.1 + 0.2 ≠ 0.3). Pour les montants, toujours NUMERIC.

Vous croiserez aussi SERIAL dans d'anciens tutoriels : il fonctionne, mais GENERATED … AS IDENTITY est la syntaxe standard à privilégier.
🔎N3  Lire et filtrer : SELECT, WHERE, ORDER BY, LIMIT
Requêtes

🎯 À quoi ça sert

La requête de base de tout le SQL : choisir des colonnes, filtrer des lignes, les trier et limiter leur nombre.

💡 Analogie — c'est une commande au restaurant : SELECT le plat, FROM la carte, WHERE sans gluten, ORDER BY du moins cher au plus cher, LIMIT 3 propositions.

🧩 Syntaxe

SQL
SELECT colonne1, colonne2        -- quelles colonnes
FROM table                        -- depuis quelle table
WHERE condition                   -- quelles lignes garder
ORDER BY colonne [ASC | DESC]     -- dans quel ordre
LIMIT n;                          -- combien de lignes au maximum

🔬 Exemple commenté

Les 3 meilleurs buteurs parmi les attaquants ayant marqué au moins 4 buts :

SQL
SELECT nom, poste, buts
FROM joueurs
WHERE poste = 'attaquant' AND buts >= 4
ORDER BY buts DESC
LIMIT 3;

1. AND est prioritaire sur OR. On veut les attaquants à plus de 3 buts ou les milieux… mais sans parenthèses, la requête ne fait pas ce qu'on croit :
SQL
SELECT nom FROM joueurs
WHERE buts > 3 AND poste = 'attaquant' OR poste = 'milieu';
▶ Résultat 6 lignes

Lu par PostgreSQL : (buts > 3 AND attaquant) OR milieu. Mettez toujours des parenthèses quand vous mélangez AND et OR.

2. = NULL ne trouve jamais rien. NULL signifie « inconnu » : on le teste avec IS NULL ou IS NOT NULL. WHERE equipe_id = NULL renvoie 0 ligne, même si Sami Koné n'a pas de club.
🔗N4  Relier des tables : les jointures
Requêtes

🎯 À quoi ça sert

Les données sont réparties dans plusieurs tables pour éviter les doublons : le nom de l'équipe est stocké une seule fois dans equipes, et chaque joueur y fait référence par equipe_id. La jointure reconstitue l'information complète.

💡 Analogie — deux listes d'invités. INNER JOIN ne garde que les personnes présentes sur les deux listes. LEFT JOIN garde toute la première liste, et laisse une case vide quand la personne n'est pas sur la seconde.

🧩 Syntaxe

SQL
SELECT a.colonne, b.colonne
FROM table_a a
[INNER | LEFT] JOIN table_b b ON b.cle = a.cle;   -- a, b : alias courts

🔬 Exemple commenté

INNER JOIN : chaque joueur avec le nom de son équipe.

SQL
SELECT j.nom AS joueur, e.nom AS equipe
FROM joueurs j
INNER JOIN equipes e ON e.id = j.equipe_id
ORDER BY e.nom, j.nom;
▶ Résultat 9 lignes

9 lignes sur 10 joueurs : Sami Koné, sans club, a disparu.

LEFT JOIN : garder tous les joueurs, puis isoler ceux qui n'ont pas d'équipe.

SQL
SELECT j.nom AS joueur, e.nom AS equipe
FROM joueurs j
LEFT JOIN equipes e ON e.id = j.equipe_id
WHERE e.id IS NULL;               -- aucune équipe correspondante

Le LEFT JOIN a conservé Sami Koné avec NULL côté équipe.

⚠️ Piège fréquent

Un INNER JOIN fait disparaître silencieusement les lignes sans correspondance : aucun message d'erreur, juste des résultats incomplets. Posez-vous toujours la question : ai-je besoin de toutes les lignes de la table de gauche ? Si oui, c'est un LEFT JOIN.
📊N5  Regrouper et agréger : GROUP BY, HAVING
Requêtes

🎯 À quoi ça sert

Passer du détail à la synthèse : combien de joueurs par équipe, combien de buts au total, quelle moyenne… Les fonctions d'agrégat (COUNT, SUM, AVG, MIN, MAX) résument un groupe de lignes en une seule.

💡 Analogie — trier un paquet de cartes par couleur, puis compter chaque tas. WHERE retire des cartes avant de faire les tas, HAVING retire des tas après les avoir comptés.

🧩 Syntaxe

SQL
SELECT colonne_de_groupe, AGREGAT(colonne)
FROM table
WHERE condition_sur_les_lignes        -- filtre AVANT le regroupement
GROUP BY colonne_de_groupe
HAVING condition_sur_les_groupes;     -- filtre APRÈS le regroupement

🔬 Exemple commenté

Nombre de joueurs et total de buts par équipe, en ne gardant que les équipes à 5 buts ou plus :

SQL
SELECT e.nom        AS equipe,
       COUNT(j.id)  AS nb_joueurs,
       SUM(j.buts)  AS total_buts
FROM equipes e
LEFT JOIN joueurs j ON j.equipe_id = e.id
GROUP BY e.nom
HAVING SUM(j.buts) >= 5
ORDER BY total_buts DESC;
▶ Résultat 3 lignes
equipenb_joueurstotal_buts
PSG29
RC Lens27
OM25

⚠️ Piège fréquent

Toute colonne du SELECT qui n'est pas dans un agrégat doit figurer dans le GROUP BY. Sinon PostgreSQL refuse, car il ne sait pas quel joueur afficher pour une équipe qui en compte plusieurs :
SQL
SELECT e.nom, j.nom, COUNT(*)
FROM equipes e JOIN joueurs j ON j.equipe_id = e.id
GROUP BY e.nom;
✖ Erreur PostgreSQL
ERROR:  column "j.nom" must appear in the GROUP BY clause or be used in an aggregate function

🧱N6  Les CTE : découper une requête en étapes
CTE

🎯 À quoi ça sert

Une CTE (Common Table Expression) est un résultat intermédiaire nommé, défini avec WITH, que la requête principale utilise comme une table. On découpe ainsi un calcul complexe en étapes lisibles, au lieu d'empiler des sous-requêtes illisibles.

💡 Analogie — une recette de cuisine. Au lieu d'une seule phrase interminable, on écrit : étape 1, préparer la pâte ; étape 2, préparer la garniture ; étape 3, assembler. Chaque CTE est une étape nommée.

🧩 Syntaxe

SQL
WITH etape_1 AS (
    SELECT ...                    -- premier calcul
),
etape_2 AS (                      -- virgule entre les CTE, un seul WITH
    SELECT ... FROM etape_1       -- une CTE peut utiliser la précédente
)
SELECT ... FROM etape_2;          -- requête principale

🔬 Exemple commenté

Calculer le classement du championnat à partir des matchs. Difficulté : chaque match concerne deux équipes (domicile et extérieur). On procède en trois étapes :

SQL
-- Étape 1 : une ligne par équipe et par match, quel que soit le côté
WITH resultats AS (
    SELECT equipe_dom_id AS equipe_id, buts_dom AS pour, buts_ext AS contre FROM matchs
    UNION ALL
    SELECT equipe_ext_id, buts_ext, buts_dom FROM matchs
),
-- Étape 2 : les points obtenus (3 victoire, 1 nul, 0 défaite)
points AS (
    SELECT equipe_id, pour, contre,
           CASE WHEN pour > contre THEN 3
                WHEN pour = contre THEN 1
                ELSE 0 END AS pts
    FROM resultats
)
-- Étape 3 : le classement
SELECT e.nom                   AS equipe,
       SUM(p.pts)              AS points,
       SUM(p.pour)             AS buts_pour,
       SUM(p.pour - p.contre)  AS difference
FROM points p
JOIN equipes e ON e.id = p.equipe_id
GROUP BY e.nom
ORDER BY points DESC, difference DESC;
▶ Résultat 6 lignes
equipepointsbuts_pourdifference
RC Lens1396
PSG10115

Stade Rennais14-7
Chaque étape se teste seule : remplacez la requête finale par SELECT * FROM resultats; pour vérifier l'étape 1.

⚠️ Piège fréquent

Une CTE n'existe que le temps de la requête qui la suit. Après le point-virgule, elle disparaît : SELECT * FROM resultats; seul provoque l'erreur relation "resultats" does not exist. Autre erreur classique : répéter WITH devant chaque CTE, alors qu'un seul WITH suffit, les CTE étant séparées par des virgules.
🌳N7  Les CTE récursives : parcourir une hiérarchie
CTE

🎯 À quoi ça sert

Certaines données forment une hiérarchie : un genre musical a des sous-genres, qui ont eux-mêmes des sous-genres. On ne connaît pas la profondeur à l'avance. Une CTE récursive se rappelle elle-même, niveau après niveau, jusqu'à ce qu'il n'y ait plus rien à trouver.

💡 Analogie — un arbre généalogique. On part de l'ancêtre (ancrage), on cherche ses enfants, puis les enfants de ses enfants (étape récursive), et on s'arrête quand une génération n'a plus de descendants (condition d'arrêt).

🧩 Syntaxe

SQL
WITH RECURSIVE nom_cte AS (
    SELECT ...                    -- 1. ANCRAGE : le point de départ
    UNION ALL
    SELECT ...                    -- 2. ÉTAPE RÉCURSIVE : utilise nom_cte
    FROM table
    JOIN nom_cte ON ...           --    s'arrête quand elle ne renvoie plus rien
)
SELECT * FROM nom_cte;

Le principe se voit avec un simple compteur :

SQL
WITH RECURSIVE compteur AS (
    SELECT 1 AS n                  -- ancrage : on part de 1
    UNION ALL
    SELECT n + 1 FROM compteur     -- étape : on ajoute 1
    WHERE n < 5                    -- condition d'arrêt
)
SELECT n FROM compteur;
▶ Résultat 5 lignes
n
1
2
3
4
5

🔬 Exemple commenté

Afficher l'arbre complet des genres musicaux avec leur chemin :

SQL
WITH RECURSIVE arbre AS (
    -- Ancrage : les genres racines (sans parent)
    SELECT id, nom, parent_id, 1 AS niveau, nom::TEXT AS chemin
    FROM genres
    WHERE parent_id IS NULL

    UNION ALL

    -- Étape : les enfants des genres déjà trouvés
    SELECT g.id, g.nom, g.parent_id, a.niveau + 1, a.chemin || ' > ' || g.nom
    FROM genres g
    JOIN arbre a ON g.parent_id = a.id
)
SELECT niveau, chemin
FROM arbre
ORDER BY chemin;

Retrouver tous les descendants d'un genre, quelle que soit la profondeur :

SQL
WITH RECURSIVE descendants AS (
    SELECT id, nom FROM genres WHERE nom = 'Rock'           -- ancrage
    UNION ALL
    SELECT g.id, g.nom
    FROM genres g
    JOIN descendants d ON g.parent_id = d.id                -- enfants
)
SELECT nom FROM descendants;

⚠️ Piège fréquent

Oublier la condition d'arrêt, ou parcourir des données qui forment une boucle (A → B → A), fait tourner la requête indéfiniment. Sur un arbre propre, l'arrêt est naturel ; sur un graphe (réseau d'amis, acteurs ayant tourné ensemble), il faut limiter la profondeur ou mémoriser le chemin parcouru pour ne pas repasser deux fois au même endroit.
🏆N8  Fonctions de fenêtrage : classer
Fenêtrage

🎯 À quoi ça sert

Une fonction de fenêtrage calcule une valeur en regardant d'autres lignes, sans les fusionner. Contrairement à GROUP BY, qui écrase un groupe en une seule ligne, chaque ligne garde son identité et reçoit une information supplémentaire : son rang, la moyenne de son groupe, etc.

💡 Analogie — un classement de course. Chaque coureur reste une personne distincte (pas de fusion), mais on lui colle un dossard « 1er », « 2e »… Le PARTITION BY, c'est faire un classement séparé par catégorie d'âge.

🧩 Syntaxe

SQL
FONCTION() OVER (
    PARTITION BY colonne     -- optionnel : un calcul séparé par groupe
    ORDER BY colonne         -- l'ordre qui détermine le rang
)
FonctionEn cas d'égalitéExemple de rangs
ROW_NUMBER()Numéros uniques, départage arbitraire1, 2, 3, 4
RANK()Même rang, puis saut1, 1, 3, 4
DENSE_RANK()Même rang, sans saut1, 1, 2, 3

🔬 Exemple commenté

Les trois fonctions côte à côte, avec un classement séparé par jeu :

SQL
SELECT jeu, pseudo, score,
       ROW_NUMBER() OVER (PARTITION BY jeu ORDER BY score DESC) AS row_number,
       RANK()       OVER (PARTITION BY jeu ORDER BY score DESC) AS rank,
       DENSE_RANK() OVER (PARTITION BY jeu ORDER BY score DESC) AS dense_rank
FROM parties
ORDER BY jeu, score DESC;

⚠️ Piège fréquent

1. Impossible de filtrer une fonction de fenêtrage dans le WHERE, car le WHERE est évalué avant le calcul des rangs :
SQL
SELECT pseudo
FROM parties
WHERE ROW_NUMBER() OVER (ORDER BY score DESC) <= 3;
✖ Erreur PostgreSQL
ERROR:  window functions are not allowed in WHERE
Solution : calculer le rang dans une sous-requête ou une CTE, puis filtrer à l'extérieur (voir le podium ci-dessus).

2. ROW_NUMBER avec des égalités donne un résultat qui peut changer d'une exécution à l'autre. Ajoutez un critère de départage : ORDER BY score DESC, date_partie.
📈N9  Fonctions de fenêtrage : cumuler et comparer
Fenêtrage

🎯 À quoi ça sert

Les fonctions de fenêtrage répondent aussi aux questions d'évolution : total cumulé depuis le début, variation par rapport à la période précédente, moyenne glissante sur les derniers mois.

💡 Analogie — en voiture, SUM() OVER est le compteur kilométrique (il cumule), LAG est le rétroviseur (la ligne précédente), LEAD le pare-brise (la ligne suivante), et la moyenne glissante le régulateur qui lisse les à-coups.

🧩 Syntaxe

SQL
SUM(col)  OVER (PARTITION BY ... ORDER BY ...)          -- cumul
LAG(col)  OVER (PARTITION BY ... ORDER BY ...)          -- valeur de la ligne précédente
LEAD(col) OVER (PARTITION BY ... ORDER BY ...)          -- valeur de la ligne suivante
AVG(col)  OVER (ORDER BY ...
                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)  -- fenêtre de 3 lignes

🔬 Exemple commenté

Cumul des écoutes et variation mensuelle d'un artiste :

SQL
SELECT artiste,
       TO_CHAR(mois, 'YYYY-MM') AS mois,
       ecoutes,
       SUM(ecoutes) OVER (PARTITION BY artiste ORDER BY mois)            AS cumul,
       ecoutes - LAG(ecoutes) OVER (PARTITION BY artiste ORDER BY mois)  AS variation
FROM streams
WHERE artiste = 'Nova'
ORDER BY mois;

Moyenne glissante sur 3 mois et aperçu du mois suivant :

SQL
SELECT artiste,
       TO_CHAR(mois, 'YYYY-MM') AS mois,
       ecoutes,

           PARTITION BY artiste ORDER BY mois
           ROWS BETWEEN 2 PRECEDING AND CURRENT ROW      -- le mois et les 2 précédents

       LEAD(ecoutes) OVER (PARTITION BY artiste ORDER BY mois) AS mois_suivant

Combiner CTE et fenêtrage : l'évolution des points au fil des journées pour les deux premiers du championnat.

SQL
WITH resultats AS (
    SELECT journee, equipe_dom_id AS equipe_id,
           CASE WHEN buts_dom > buts_ext THEN 3
                WHEN buts_dom = buts_ext THEN 1 ELSE 0 END AS pts
    FROM matchs
    UNION ALL
    SELECT journee, equipe_ext_id,
           CASE WHEN buts_ext > buts_dom THEN 3

    FROM matchs
)

⚠️ Piège fréquent

Avec un ORDER BY et sans cadre précisé, PostgreSQL utilise par défaut RANGE : les lignes à égalité sont cumulées ensemble. Sur des valeurs uniques (des mois), aucun souci ; sur des scores égaux, le cumul surprend :
SQL
SELECT jeu, pseudo, score,
       SUM(score) OVER (PARTITION BY jeu ORDER BY score DESC) AS cumul_range,
       SUM(score) OVER (PARTITION BY jeu ORDER BY score DESC
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumul_rows
FROM parties
WHERE jeu = 'Tetris'
ORDER BY score DESC, pseudo;

🧭 Ordre d'exécution logique d'une requête

PostgreSQL n'exécute pas une requête dans l'ordre où on l'écrit. Cet ordre explique la plupart des erreurs de la séance :

Ordre d'exécution
1. FROM / JOIN      -- quelles tables, reliées comment
2. WHERE            -- filtrer les lignes
3. GROUP BY         -- former les groupes
4. HAVING           -- filtrer les groupes
5. SELECT           -- calculer les colonnes (dont les fonctions de fenêtrage)
6. ORDER BY         -- trier
7. LIMIT            -- couper
💡 C'est pour cela qu'on ne peut pas utiliser un alias du SELECT dans le WHERE, ni une fonction de fenêtrage dans le WHERE : au moment du filtre, ils n'existent pas encore.

Cadre (frame) Fenêtrage

Sous-ensemble de la partition pris en compte pour le calcul, défini par ROWS ou RANGE BETWEEN…

Clé primaire Structure

Colonne (ou groupe de colonnes) qui identifie chaque ligne de façon unique.

Clé étrangère Structure

Colonne qui fait référence à la clé primaire d'une autre table et garantit que la référence existe.

Collation Fenêtrage

Règles de tri et de comparaison du texte (ordre alphabétique, accents), qui dépendent de la configuration du serveur.

Contrainte Structure

Règle vérifiée par la base à chaque écriture : NOT NULL, UNIQUE, CHECK, clé primaire, clé étrangère.

CTE CTE

Common Table Expression : résultat intermédiaire nommé défini avec WITH et utilisé par la requête qui suit.

CTE récursive CTE

CTE qui s'appelle elle-même pour parcourir une hiérarchie ou un graphe (WITH RECURSIVE).

Fonction de fenêtrage Fenêtrage

Fonction qui calcule une valeur à partir d'un ensemble de lignes liées, sans les fusionner (mot-clé OVER).

HAVING Requêtes

Filtre appliqué aux groupes après le GROUP BY, contrairement à WHERE qui filtre les lignes avant.

IDENTITY Structure

Colonne dont la valeur est générée automatiquement (1, 2, 3…), syntaxe standard pour les identifiants.

Jointure Requêtes

Opération qui relie les lignes de deux tables selon une condition. INNER garde les correspondances, LEFT garde toute la table de gauche.

LAG / LEAD Fenêtrage

Renvoient la valeur de la ligne précédente / suivante dans l'ordre de la fenêtre.

Méta-commande Prise en main

Commande propre à psql, commençant par \ (ex. \dt). Ce n'est pas du SQL et elle ne prend pas de point-virgule.

NULL Requêtes

Absence de valeur, « inconnu ». Se teste avec IS NULL, jamais avec = NULL.

PARTITION BY Fenêtrage

Découpe les lignes en groupes indépendants pour une fonction de fenêtrage.
