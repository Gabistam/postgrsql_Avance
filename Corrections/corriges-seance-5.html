🔍Cas 2 — Les intruses

Groupe 1 · Verrou de ligne (SELECT … FOR UPDATE) Concurrence

  • ✔ Lire le solde d'un compte, puis décider si le paiement est accepté.
  • ✔ Vérifier le stock restant avant de valider une commande.
  • ✔ Réserver la dernière place d'un concert après avoir vérifié qu'elle est libre.
  • ✔ Lire un score, le modifier dans l'application, puis l'écrire.
  • 🎯 Intruse — Répartir des tâches entre dix workers sans qu'aucun n'attende les autres.
💡 Pour qu'un worker saute les tâches déjà prises au lieu d'attendre, il faut FOR UPDATE SKIP LOCKED.

Groupe 2 · Niveau SERIALIZABLE Transactions

  • ✔ Au moins un médecin doit toujours rester de garde.
  • ✔ Le budget total des dépenses d'une équipe ne doit jamais dépasser 10 000 €.
  • ✔ Deux réservations d'une même salle ne doivent jamais se chevaucher.
  • ✔ Un joueur ne peut pas rejoindre plus de trois équipes à la fois.
  • 🎯 Intruse — Afficher un tableau de bord de ventes rafraîchi toutes les minutes.
💡 Une simple lecture, sans décision à la clé, n'a pas besoin d'un niveau d'isolation élevé : READ COMMITTED suffit.

Groupe 3 · Row Level Security Contrôle d'accès

  • ✔ Chaque client ne voit que ses propres factures.
  • ✔ Une application SaaS partage une base entre plusieurs entreprises clientes.
  • ✔ Les messages privés ne sont lisibles que par l'expéditeur et le destinataire.
  • ✔ Un médecin n'accède qu'aux dossiers de ses patients.
  • 🎯 Intruse — Empêcher le compte de l'application de supprimer des tables.
💡 Interdire une action sur une table entière relève des privilèges : un rôle sans droit DROP ni DELETE, pas une politique de lignes.

Groupe 4 · Rôles et privilèges Rôles

  • ✔ Créer un compte en lecture seule pour l'outil de reporting.
  • ✔ Retirer le droit DELETE au compte de l'application.
  • ✔ Réserver les migrations de schéma à un compte dédié.
  • ✔ Donner les mêmes droits à toute une équipe via un groupe.
  • 🎯 Intruse — Empêcher qu'une saisie utilisateur modifie une requête SQL.
💡 Contre l'injection SQL, la parade est la requête paramétrée : la valeur saisie ne peut jamais devenir du code.

Groupe 5 · Risque d'injection SQL Injection & secrets

  • ✔ Une recherche construite en collant le texte saisi dans la requête.
  • ✔ Un tri dont le nom de colonne vient directement de l'URL, sans validation.
  • ✔ Un EXECUTE PL/pgSQL qui concatène un paramètre avec ||.
  • ✔ Un filtre construit en JavaScript par concaténation, puis envoyé à la base.
  • 🎯 Intruse — Une requête préparée dont la valeur est passée en paramètre $1.
💡 Avec $1, la valeur voyage séparément du texte SQL : elle ne peut pas modifier la requête.
✅Cas 3 — Vrai ou faux
#AffirmationRéponseExplication
1Sans BEGIN, chaque instruction est sa propre transaction.VraiC'est le mode autocommit, par défaut dans psql, pgAdmin et DBeaver.
2Après une erreur dans une transaction, les instructions suivantes s'exécutent normalement.FauxLa transaction est avortée : tout est refusé jusqu'au ROLLBACK (ou ROLLBACK TO SAVEPOINT).
3En READ COMMITTED, deux lectures identiques dans la même transaction peuvent donner des résultats différents.VraiChaque instruction prend un nouvel instantané et voit les modifications validées entre-temps.
4Avec MVCC, une lecture bloque les écritures sur les mêmes lignes.FauxLecteurs et écrivains ne se bloquent pas : chacun travaille sur sa version des lignes.
5En REPEATABLE READ, modifier une ligne changée par une autre transaction depuis l'instantané provoque une erreur.Vraicould not serialize access due to concurrent update : la transaction doit être relancée.
6SERIALIZABLE garantit qu'aucune transaction n'échoue.FauxAu contraire : il fait échouer celles qui rendraient le résultat incohérent. L'application doit savoir les relancer.
7UPDATE … SET x = x + 1 évite la mise à jour perdue sans verrou explicite.VraiPostgreSQL relit la valeur validée au moment d'écrire.
8SKIP LOCKED fait attendre la libération des lignes verrouillées.FauxIl les ignore et passe aux suivantes, sans attendre.
9Verrouiller les lignes toujours dans le même ordre évite les interblocages.VraiL'attente circulaire devient impossible : l'une des transactions attend simplement l'autre.
10En cas d'interblocage, PostgreSQL annule les deux transactions.FauxIl en annule une seule, pour débloquer l'autre.
11L'application peut utiliser le compte postgres si le mot de passe est robuste.FauxUn superutilisateur ignore tous les droits et la RLS : une seule faille donne un accès total.
12Un rôle peut servir de groupe de droits pour d'autres rôles.VraiOn donne les droits au groupe, puis on y ajoute les comptes.
13Un superutilisateur est soumis aux politiques de Row Level Security.FauxIl les ignore toujours, comme les rôles dotés de BYPASSRLS.
14Dans une politique RLS, USING filtre les lignes existantes et WITH CHECK contrôle les lignes écrites.VraiUSING écarte silencieusement ; WITH CHECK refuse avec une erreur.
15Une fonction SECURITY DEFINER s'exécute avec les droits de l'appelant.FauxElle s'exécute avec les droits de son propriétaire : d'où la nécessité de figer son search_path.
16Par défaut, tout rôle peut exécuter une nouvelle fonction.VraiLe droit EXECUTE est accordé à PUBLIC : il faut le retirer explicitement.
17Échapper les apostrophes à la main suffit contre l'injection SQL.FauxIl existe toujours des contournements : seules les requêtes paramétrées sont fiables.
18Un nom de colonne choisi par l'utilisateur peut être passé comme paramètre $1.FauxLes paramètres ne portent que des valeurs : un identifiant se valide par liste blanche puis s'insère avec format('%I').

Écrivez lister(tri) qui renvoie le podium trié selon une colonne choisie par l'utilisateur. Un nom de colonne ne peut pas être passé en paramètre : validez-le avec une liste blanche, puis insérez-le avec format('%I'). Testez avec « pieces », puis avec une tentative d'injection.

✅ Correction

SQL
CREATE OR REPLACE FUNCTION lister(p_tri TEXT)
RETURNS TABLE (pseudo VARCHAR, pieces INTEGER)
LANGUAGE plpgsql
STABLE
AS $$
BEGIN
    IF p_tri NOT IN ('pseudo', 'pieces') THEN            -- liste blanche
        RAISE EXCEPTION 'Tri non autorisé : %', p_tri;
    END IF;
    RETURN QUERY EXECUTE
        format('SELECT pseudo, pieces FROM aventuriers ORDER BY %I DESC LIMIT 3', p_tri);
END;
$$;

M16.3Une recherche à l'abri des injections

Écrivez rechercher_films(texte), qui renvoie les 5 premiers films dont le titre contient le texte saisi, en SQL statique : la saisie n'est jamais collée dans le code SQL. Testez avec « dark », puis avec une tentative d'injection.

✅ Correction

SQL
CREATE OR REPLACE FUNCTION rechercher_films(p_texte TEXT)
RETURNS TABLE (titre VARCHAR, annee INTEGER)
LANGUAGE sql
STABLE
AS $$
    SELECT f.titre, f.annee
    FROM films f
    WHERE f.titre ILIKE '%' || p_texte || '%'     -- la saisie reste une valeur, jamais du code
    ORDER BY f.annee
    LIMIT 5;
$$;
🎯 Attendu : la commande s'exécute sans erreur.
#Instruction et résultatCe qui se passe
1
SELECT * FROM rechercher_films('dark');
titreannee
The Dark Knight2008
The Dark Knight Rises2012
2
SELECT * FROM rechercher_films($$x' OR '1'='1$$);
titreannee
Aucun titre ne contient ce texte : 0 ligne, aucune injection.
🔑 Point clé : Ici, la concaténation construit une valeur (le motif du ILIKE), pas du code SQL : c'est sans danger. Seul un % ou un _ saisi par l'utilisateur garde son sens de joker.
