🔍Cas 2 — Les intruses

Groupe 1 · Index B-tree composite Index

  • ✔ Afficher les 10 dernières commandes d'un client, de la plus récente à la plus ancienne.
  • ✔ Filtrer les matchs d'une équipe sur une saison donnée.
  • ✔ Lister les messages d'une conversation dans l'ordre chronologique.
  • ✔ Compter les ventes d'un magasin sur une plage de dates.
  • 🎯 Intruse — Rechercher les articles dont le titre contient « vélo » n'importe où.
💡 Un « contient » (ILIKE '%vélo%') commence par un joker : aucun B-tree ne peut servir. Il faut un index GIN avec pg_trgm.

Groupe 2 · Index GIN Index

  • ✔ Trouver les produits dont les tags JSONB contiennent « promo ».
  • ✔ Rechercher un joueur par un morceau de son pseudo, avec ILIKE '%…%'.
  • ✔ Tolérer les fautes de frappe dans une barre de recherche.
  • ✔ Filtrer des annonces sur une caractéristique stockée dans un JSONB (@>).
  • 🎯 Intruse — Trouver les réservations comprises entre deux dates.
💡 Une plage de dates est le cas d'école du B-tree : les valeurs sont triées, la plage est lue d'un seul tenant.

Groupe 3 · Index partiel Index

  • ✔ Retrouver vite les commandes « non livrées », 2 % de la table.
  • ✔ Lister les tickets de support encore ouverts.
  • ✔ Afficher les notifications non lues d'un utilisateur.
  • ✔ Surveiller les paiements en échec, rares mais consultés souvent.
  • 🎯 Intruse — Filtrer les utilisateurs actifs, qui représentent 85 % de la table.
💡 Une condition vraie pour 85 % des lignes n'est pas sélective : un index partiel serait presque aussi gros qu'un index complet, et PostgreSQL préférerait sans doute tout lire.

Groupe 4 · Réécrire la requête plutôt que créer un index Optimisation

  • ✔ WHERE date_creation::DATE = '2025-03-14' alors qu'un index existe sur date_creation.
  • ✔ Une pagination avec OFFSET 500000.
  • ✔ WHERE EXTRACT(YEAR FROM date_commande) = 2025.
  • ✔ Un SELECT * qui empêche un Index Only Scan possible.
  • 🎯 Intruse — Un filtre très sélectif sur une colonne qui n'a aucun index.
💡 Ici, la requête est bien écrite : il manque simplement un index sur la colonne filtrée.

Groupe 5 · Maintenance : ANALYZE ou VACUUM Maintenance

  • ✔ Après un import d'un million de lignes, le planificateur estime 10 lignes au lieu de 50 000.
  • ✔ Un Index Only Scan affiche des milliers de Heap Fetches.
  • ✔ Une table a beaucoup grossi après de nombreuses suppressions.
  • ✔ Les estimations d'un plan sont très éloignées des lignes réelles.
  • 🎯 Intruse — Un Sort coûteux apparaît juste avant un LIMIT 10.
💡 Un tri avant un LIMIT se supprime avec un index composite qui fournit déjà l'ordre, pas avec de la maintenance.
✅Cas 3 — Vrai ou faux
#AffirmationRéponseExplication
1EXPLAIN exécute la requête pour en mesurer le temps.FauxC'est EXPLAIN ANALYZE qui exécute. EXPLAIN seul n'affiche que le plan estimé.
2EXPLAIN ANALYZE sur un DELETE supprime réellement les lignes.VraiLa requête est exécutée : encadrez-la d'un BEGIN et d'un ROLLBACK.
3Un plan se lit de l'intérieur vers l'extérieur.VraiLes nœuds les plus indentés s'exécutent d'abord et alimentent leur parent.
4Si un index existe sur la colonne filtrée, PostgreSQL l'utilise toujours.FauxIl l'ignore si la condition ramène une grande part de la table : tout lire est alors moins coûteux.
5Les Buffers sont une mesure plus stable que le temps d'exécution.VraiLe nombre de blocs lus dépend peu de la machine et de sa charge, contrairement au temps.
6Un Index Only Scan ne lit jamais la table.FauxIl la consulte (Heap Fetches) pour les blocs dont la visibilité n'est pas garantie par la carte de visibilité.
7Un index composite (a, b) sert pour un filtre sur b seul.FauxIl faut filtrer sur la première colonne ; b seul oblige à parcourir tout l'index, voire toute la table.
8Un index sur LOWER(email) sert pour WHERE LOWER(email) = '…'.VraiC'est exactement l'expression indexée.
9Un index sur LOWER(email) sert pour WHERE email ILIKE '…'.FauxL'expression est différente : l'index n'est pas utilisable.
10L'index GIN sur un JSONB accélère les filtres avec ->>.FauxIl sert les opérateurs de contenance (@>, ?). Pour ->>, il faut un index B-tree sur l'expression.
11ILIKE '%mot%' peut utiliser un index.VraiOui, un index GIN avec la classe gin_trgm_ops de l'extension pg_trgm.
12La pagination par OFFSET devient plus lente à mesure que le numéro de page augmente.VraiPostgreSQL lit puis jette toutes les lignes sautées.
13Chaque index ajouté ralentit les insertions.VraiChaque ligne insérée met à jour tous les index de la table.
14ANALYZE récupère l'espace des lignes supprimées.FauxC'est le rôle de VACUUM. ANALYZE recalcule les statistiques.
15pg_stat_statements regroupe les requêtes identiques qui ne diffèrent que par leurs valeurs.VraiLes valeurs sont remplacées par $1, $2… : on voit le coût cumulé d'un même type de requête.
16Une optimisation proposée par une IA peut être appliquée sans mesure si elle semble logique.FauxChaque proposition est une hypothèse : on mesure avant et après, et on vérifie que le résultat est identique.

2Une procédure peut renvoyer une valeur grâce à un paramètre INOUT.VraiElle ne renvoie rien avec RETURN, mais ses paramètres INOUT sont renvoyés à l'appelant.

9Dans un trigger BEFORE, RETURN NULL annule l'écriture de la ligne.VraiSilencieusement, sans aucune erreur : c'est souvent un oubli de RETURN NEW.

15Quand plusieurs triggers répondent au même événement, PostgreSQL les exécute dans l'ordre de création.FauxIl les exécute par ordre alphabétique de leur nom.

26.2Revendre un objet

Écrivez la procédure vendre(pseudo, objet, INOUT gain) : l'aventurier revend un exemplaire d'un objet de son inventaire à la moitié de son prix. L'objet retourne en boutique, les pièces sont créditées, et la ligne d'inventaire disparaît s'il n'en reste plus. Zed revend son épée courte.

✅ Correction

SQL
CREATE OR REPLACE PROCEDURE vendre(p_pseudo TEXT, p_objet TEXT, INOUT p_gain INTEGER DEFAULT NULL)
LANGUAGE plpgsql
AS $$
DECLARE
    v_av_id  INTEGER;
    v_obj    objets%ROWTYPE;
    v_qte    INTEGER;
BEGIN
    SELECT id INTO v_av_id FROM aventuriers WHERE pseudo = p_pseudo;
    IF NOT FOUND THEN RAISE EXCEPTION 'Aventurier inconnu : %', p_pseudo; END IF;
    SELECT * INTO v_obj FROM objets WHERE nom = p_objet;
    IF NOT FOUND THEN RAISE EXCEPTION 'Objet inconnu : %', p_objet; END IF;

    SELECT quantite INTO v_qte FROM inventaire
    WHERE aventurier_id = v_av_id AND objet_id = v_obj.id;
    IF NOT FOUND THEN
        RAISE EXCEPTION '% ne possède pas « % »', p_pseudo, p_objet
              USING HINT = 'Consultez votre inventaire avant de vendre.';
    END IF;

    p_gain := v_obj.prix / 2;
    IF v_qte = 1 THEN
        DELETE FROM inventaire WHERE aventurier_id = v_av_id AND objet_id = v_obj.id;
    ELSE
        UPDATE inventaire SET quantite = quantite - 1
        WHERE aventurier_id = v_av_id AND objet_id = v_obj.id;
    END IF;
    UPDATE objets      SET stock  = stock  + 1      WHERE id = v_obj.id;
    UPDATE aventuriers SET pieces = pieces + p_gain WHERE id = v_av_id;
END;
$$;

CREATE OR REPLACE PROCEDURE noter(p_pseudo TEXT, p_titre TEXT, p_note NUMERIC,
                                  INOUT p_moyenne NUMERIC DEFAULT NULL)
LANGUAGE plpgsql
AS $$
DECLARE
    v_user  INTEGER;
    v_film  INTEGER;
BEGIN
    IF p_note NOT BETWEEN 0.5 AND 5 OR p_note * 2 <> TRUNC(p_note * 2) THEN
        RAISE EXCEPTION 'Note invalide : % (de 0,5 à 5, par demi-point)', p_note;
    END IF;
    SELECT id INTO v_user FROM utilisateurs WHERE pseudo = p_pseudo;
    IF NOT FOUND THEN RAISE EXCEPTION 'Membre inconnu : %', p_pseudo; END IF;
    SELECT id INTO v_film FROM films WHERE titre = p_titre;
    IF NOT FOUND THEN RAISE EXCEPTION 'Film inconnu : %', p_titre; END IF;

    INSERT INTO notes (utilisateur_id, film_id, note, note_le)
    VALUES (v_user, v_film, p_note, CURRENT_DATE)
    ON CONFLICT (utilisateur_id, film_id)
        DO UPDATE SET note = EXCLUDED.note, note_le = EXCLUDED.note_le;
    INSERT INTO journal (utilisateur_id, film_id, date_visionnage)
    VALUES (v_user, v_film, CURRENT_DATE);

    SELECT ROUND(AVG(note), 2) INTO p_moyenne FROM notes WHERE film_id = v_film;
END;
$$;

M13.3Initialiser les statistiques par lots

La table films_stats est vide. Écrivez recalculer_stats(lot) qui calcule, film par film, le nombre de notes et la moyenne, en validant tous les lot films. Lancez-la par lots de 10.

CREATE OR REPLACE PROCEDURE recalculer_stats(p_lot INTEGER)
LANGUAGE plpgsql
AS $$
DECLARE
    r    RECORD;
    v_n  INTEGER := 0;
BEGIN
    FOR r IN SELECT DISTINCT film_id FROM notes ORDER BY film_id LOOP
        INSERT INTO films_stats (film_id, nb_notes, moyenne)
        SELECT film_id, COUNT(*), ROUND(AVG(note), 2) FROM notes
        WHERE film_id = r.film_id GROUP BY film_id
        ON CONFLICT (film_id)
            DO UPDATE SET nb_notes = EXCLUDED.nb_notes, moyenne = EXCLUDED.moyenne;
        v_n := v_n + 1;
        IF v_n % p_lot = 0 THEN
            COMMIT;
            RAISE NOTICE '% films traités', v_n;
        END IF;
    END LOOP;
    COMMIT;
END;
$$;

CREATE OR REPLACE FUNCTION trg_films_stats()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_film INTEGER := CASE WHEN TG_OP = 'DELETE' THEN OLD.film_id ELSE NEW.film_id END;
BEGIN

    SELECT v_film, COUNT(*), COALESCE(ROUND(AVG(note), 2), 0)

END;
$$;
