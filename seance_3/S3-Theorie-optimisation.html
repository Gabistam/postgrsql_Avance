-- =====================================================================
--  Complément séance 3 — SQL avancé avec PostgreSQL
--  À exécuter sur la base cours_sql (indépendant des autres tables).
--  Génère une plateforme de streaming musical volumineuse :
--  5 000 artistes, 50 000 utilisateurs, 200 000 morceaux, 1 000 000 d'écoutes.
--  Données fictives et déterministes : tout le monde obtient les mêmes lignes.
--  Durée : 10 à 60 secondes selon la machine.
--  Script ré-exécutable : il supprime puis recrée ses tables (et leurs index).
-- =====================================================================

DROP TABLE IF EXISTS ecoutes, morceaux, utilisateurs_app, artistes CASCADE;

CREATE TABLE artistes (
    id     INTEGER PRIMARY KEY,
    nom    VARCHAR(60) NOT NULL,
    pays   VARCHAR(2)  NOT NULL
);

CREATE TABLE utilisateurs_app (
    id          INTEGER PRIMARY KEY,
    pseudo      VARCHAR(30) NOT NULL,
    pays        VARCHAR(2)  NOT NULL,
    inscrit_le  DATE        NOT NULL
);

CREATE TABLE morceaux (
    id          INTEGER PRIMARY KEY,
    artiste_id  INTEGER NOT NULL REFERENCES artistes(id),
    titre       VARCHAR(80) NOT NULL,
    infos       JSONB NOT NULL                 -- tags, bpm, explicite
);

CREATE TABLE ecoutes (
    id              BIGINT PRIMARY KEY,
    utilisateur_id  INTEGER   NOT NULL REFERENCES utilisateurs_app(id),
    morceau_id      INTEGER   NOT NULL REFERENCES morceaux(id),
    ecoute_le       TIMESTAMP NOT NULL,
    duree_s         INTEGER   NOT NULL,        -- secondes écoutées
    plateforme      VARCHAR(10) NOT NULL,      -- mobile, web, tv, enceinte
    terminee        BOOLEAN   NOT NULL         -- morceau écouté jusqu'au bout ?
);

🔭N18  Lire un plan : EXPLAIN et EXPLAIN ANALYZE
Plans

🎯 À quoi ça sert

Avant d'optimiser, il faut savoir ce que fait PostgreSQL. Le planificateur choisit, pour chaque requête, une stratégie : quelles tables lire, dans quel ordre, avec quel index. EXPLAIN affiche ce plan sans exécuter la requête ; EXPLAIN ANALYZE l'exécute et ajoute les mesures réelles.

💡 Analogie — le GPS qui propose un itinéraire (EXPLAIN) puis le trajet réellement parcouru, avec le temps et les bouchons rencontrés (EXPLAIN ANALYZE). On compare l'estimation et la réalité pour trouver où ça coince.

🧩 Syntaxe

SQL
EXPLAIN requête;                              -- plan estimé, requête NON exécutée
EXPLAIN ANALYZE requête;                      -- exécute et mesure
EXPLAIN (ANALYZE, BUFFERS) requête;           -- + blocs de données lus

-- Pendant cette séance, plans plus lisibles sans parallélisme :
SET max_parallel_workers_per_gather = 0;      -- valable pour la session en cours
Élément du planSignification
cost=0.00..20765.00Coût estimé (unité abstraite) : avant la 1re ligne .. pour toutes les lignes
rows=20Nombre de lignes estimé par le planificateur
actual time=0.01..47.1Temps réel en ms : 1re ligne .. dernière ligne
rows=20 loops=1Lignes réellement produites, et nombre d'exécutions du nœud
Rows Removed by FilterLignes lues pour rien : le signal n°1 d'un index manquant
Buffers: shared hit / readBlocs de 8 Ko lus en mémoire (hit) ou sur disque (read) : la vraie mesure du travail
Execution TimeTemps total d'exécution
📌 Un plan se lit de l'intérieur vers l'extérieur : les lignes les plus indentées (précédées de ->) s'exécutent en premier et alimentent leur parent.

🔬 Exemple commenté

Retrouver les écoutes de l'utilisateur 4242. Par défaut, PostgreSQL répartit la lecture entre plusieurs processus (workers) que le nœud Gather rassemble :

Plan estimé seulement : la requête n'a pas été exécutée.

⚠️ Piège fréquent

EXPLAIN ANALYZE exécute réellement la requête. Sur un UPDATE ou un DELETE, les données sont modifiées ! Pour analyser une écriture sans conséquence, encadrez-la : BEGIN; EXPLAIN ANALYZE DELETE …; ROLLBACK;
🚪N19  Les modes de lecture d'une table
Accès & jointures

🎯 À quoi ça sert

Pour lire une table, PostgreSQL a plusieurs stratégies. Il choisit celle qui lui semble la moins coûteuse selon le nombre de lignes attendues. Un index n'est pas toujours la meilleure option : pour ramener 60 % d'une table, tout lire d'un bloc est plus rapide que sauter d'une page à l'autre.

💡 Analogie — une bibliothèque. Seq Scan : parcourir tous les rayons. Index Scan : consulter le fichier puis aller chercher chaque livre. Bitmap Scan : noter toutes les cotes, les trier par rayon, puis faire une seule tournée. Index Only Scan : la fiche du fichier contient déjà l'information, inutile d'aller en rayon.

🧩 Syntaxe

ModePrincipeQuand PostgreSQL le choisit
Seq ScanLit toute la table, bloc après blocPas d'index utilisable, ou une grande part de la table à lire
Index ScanParcourt l'index, puis lit chaque ligne dans la tableTrès peu de lignes, ou un ordre fourni par l'index
Bitmap Heap ScanRepère toutes les lignes dans l'index, puis lit les blocs dans l'ordreQuelques dizaines à quelques milliers de lignes
Index Only ScanRépond avec l'index seul, sans lire la tableToutes les colonnes demandées sont dans l'index
SQL
CREATE INDEX nom_index ON table (colonne);

⚠️ Piège fréquent

Croire qu'un index est utilisé dès qu'il existe. PostgreSQL l'ignore si la condition est peu sélective (beaucoup de lignes ramenées), si les statistiques sont fausses, ou si la requête est écrite d'une façon qui l'empêche de s'en servir (N24). Seul le plan fait foi.
🔗N20  Jointures et statistiques du planificateur
Accès & jointures

🎯 À quoi ça sert

Pour joindre deux tables, PostgreSQL choisit entre trois algorithmes. Son choix repose sur une estimation du nombre de lignes, elle-même tirée des statistiques qu'il tient sur chaque colonne. Des statistiques fausses donnent des estimations fausses, donc de mauvais plans.

💡 Analogie — trois façons d'apparier des invités à leur table lors d'un mariage : chercher chaque invité dans la liste un par un (Nested Loop), afficher un plan de table au mur que chacun consulte (Hash Join), ou trier les deux listes par ordre alphabétique et les dérouler ensemble (Merge Join).

🧩 Syntaxe

AlgorithmePrincipeIdéal quand
Nested LoopPour chaque ligne de gauche, chercher les correspondances à droitePeu de lignes à gauche et un index à droite
Hash JoinCharger la petite table dans une table de hachage en mémoire, puis parcourir la grandeBeaucoup de lignes, jointure par égalité
Merge JoinParcourir les deux côtés déjà triés, en parallèleDeux entrées déjà triées sur la clé de jointure
SQL
ANALYZE nom_table;               -- met à jour les statistiques d'une table
SELECT * FROM pg_stats WHERE tablename = 'nom_table';   -- les consulter

WHERE tablename = 'ecoutes' AND attname IN ('plateforme', 'terminee');

PostgreSQL sait que « mobile » représente environ 60 % des lignes : c'est pour cela qu'il a estimé près de 600 000 lignes en N19 et choisi un Seq Scan. Les fréquences varient légèrement d'une installation à l'autre, car l'échantillon est tiré au hasard.

⚠️ Piège fréquent

Charger ou modifier massivement une table, puis l'interroger aussitôt. Tant que les statistiques ne sont pas recalculées, le planificateur raisonne sur l'ancienne table et peut choisir un plan catastrophique. Le processus autovacuum finit par les mettre à jour, mais après un gros import, lancez ANALYZE vous-même. Signal d'alerte dans un plan : un rows= estimé très éloigné du rows= réel.

🚦 Point d'étape

Vous savez lire un plan, reconnaître un Seq Scan qui trahit un index manquant, et comprendre pourquoi PostgreSQL choisit une stratégie. Place aux index eux-mêmes : lequel créer, sur quelles colonnes, dans quel ordre.

🌲N21  L'index B-tree, simple et composite
Index

🎯 À quoi ça sert

Le B-tree est l'index par défaut. Il range les valeurs triées dans un arbre, ce qui permet de trouver une valeur, une plage de valeurs ou de fournir des lignes déjà triées. Un index composite porte sur plusieurs colonnes : l'ordre de ces colonnes est décisif.

💡 Analogie — un annuaire téléphonique trié par nom puis par prénom. Trouver tous les « Martin », puis « Martin Hugo », est immédiat. Trouver tous les « Hugo », quel que soit le nom, oblige à lire tout l'annuaire.

🧩 Syntaxe

SQL
CREATE INDEX nom ON table (col);                       -- simple
CREATE INDEX nom ON table (col_a, col_b DESC);           -- composite, avec sens du tri
CREATE UNIQUE INDEX nom ON table (col);                  -- garantit l'unicité

-- Un index (a, b) sert pour : WHERE a = …   |   WHERE a = … AND b …   |   WHERE a = … ORDER BY b
-- Il ne sert PAS pour :       WHERE b = …   (b n'est pas la première colonne)

⚠️ Piège fréquent

Un index composite ne sert que si la requête filtre sur sa première colonne. L'index (utilisateur_id, ecoute_le) est inutile pour une recherche par date seule :
SQL

🎯N22  Index partiel, sur expression et couvrant
Index

🎯 À quoi ça sert

Trois variantes du B-tree qui répondent à des besoins précis :

  • Partiel : n'indexe que les lignes qui vérifient une condition. Plus petit, plus rapide à maintenir.
  • Sur expression : indexe le résultat d'un calcul, pour les requêtes qui filtrent sur ce calcul.
  • Couvrant (INCLUDE) : embarque des colonnes supplémentaires pour répondre sans lire la table.
💡 Analogie — un index partiel, c'est le carnet où un disquaire ne note que les disques en rupture de stock : il est mince et répond vite à la seule question qu'on lui pose.

🧩 Syntaxe

SQL
CREATE INDEX nom ON table (col) WHERE condition;          -- partiel
CREATE INDEX nom ON table (LOWER(col));                   -- sur expression
CREATE INDEX nom ON table (col) INCLUDE (col2, col3);     -- couvrant

🧬N23  Index GIN : JSONB et recherche dans le texte

🎯 À quoi ça sert

Le B-tree indexe une valeur par ligne. Pour chercher à l'intérieur d'une valeur (un élément dans un tableau JSONB, un mot au milieu d'un titre), il faut un index GIN (Generalized Inverted Index). Il fonctionne comme l'index d'un livre : pour chaque élément, la liste des lignes qui le contiennent. C'est le prolongement direct de N13 (JSONB).

💡 Analogie — l'index à la fin d'un livre de cuisine : pour « chocolat », il donne toutes les pages où le mot apparaît, même au milieu d'une recette.

SQL
CREATE INDEX nom ON table USING GIN (colonne_jsonb);            -- @>, ?, ?| …

CREATE EXTENSION IF NOT EXISTS pg_trgm;                          -- une fois par base
CREATE INDEX nom ON table USING GIN (colonne_texte gin_trgm_ops); -- LIKE / ILIKE '%…%', similarité

✍️N24  Réécrire les requêtes lentes

🎯 À quoi ça sert

♻️N25  Mesurer, entretenir, rester sobre
Maintenance

🎯 À quoi ça sert

Un index accélère les lectures mais coûte : de l'espace disque, et du travail à chaque INSERT, UPDATE ou DELETE. Le rôle du tech lead est de garder les index qui rapportent, de supprimer les autres, de repérer les requêtes qui pèsent vraiment sur le serveur, et de s'assurer que la base est entretenue.

💡 Analogie — un classeur avec des intercalaires : quelques-uns font gagner un temps fou ; cinquante rendent chaque rangement interminable, pour des onglets que personne n'ouvre.

🧩 Syntaxe

SQL
-- Taille d'une table et de ses index
SELECT pg_size_pretty(pg_relation_size('table')), pg_size_pretty(pg_indexes_size('table'));

-- Utilisation de chaque index depuis la dernière remise à zéro des statistiques
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE relname = 'table';

-- Entretien
VACUUM table;            -- récupère l'espace des lignes supprimées, tient la carte de visibilité
ANALYZE table;           -- recalcule les statistiques du planificateur
VACUUM ANALYZE table;    -- les deux

-- Les requêtes les plus coûteuses du serveur (extension pg_stat_statements)
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

🤖 Utiliser l'IA à l'étape 3 — Donnez-lui la requête, le plan complet obtenu avec EXPLAIN (ANALYZE, BUFFERS) et la définition des tables (\d table). Demandez-lui d'identifier le nœud le plus coûteux et de proposer des hypothèses. Puis traitez chaque proposition comme une hypothèse à vérifier par la mesure (étape 5) : l'IA ne voit ni vos données, ni votre charge réelle, et propose volontiers des index superflus.
🌱 Traduire un gain en sobriété — Une requête qui passe de 8 265 à 4 blocs lus, appelée 10 000 fois par jour, évite de lire environ 650 Go par jour. Moins de lectures, c'est moins de processeur, moins d'entrées/sorties disque, un serveur plus petit : c'est ainsi que l'optimisation rejoint la démarche RSE.

⚠️ Piège fréquent

Créer un index pour chaque requête lente, sans jamais faire le ménage. Chaque index ralentit toutes les écritures, alourdit les sauvegardes et consomme de la mémoire. Règle du module : un index sans gain mesuré est supprimé. C'est aussi une démarche de sobriété : moins d'index inutiles, c'est moins de stockage, moins d'écritures disque, donc moins d'énergie consommée.

📖Glossaire — Séance 3
PlansAccès & jointuresIndexOptimisationMaintenance

ANALYZE Maintenance

Commande qui recalcule les statistiques d'une table.

Autovacuum Maintenance

Processus de fond qui lance automatiquement VACUUM et ANALYZE.

B-tree Index

Index par défaut, en arbre trié : égalité, plages et tri.

Bitmap Heap Scan Accès & jointures

Repérage des lignes dans l'index, puis lecture groupée des blocs de la table.

Buffers Plans

Blocs de 8 Ko lus en mémoire (hit) ou sur disque (read) : mesure stable du travail.

Carte de visibilité Maintenance

Carte des blocs dont toutes les lignes sont visibles, nécessaire aux Index Only Scans.

Coût Plans

Estimation abstraite du travail d'un nœud, utilisée pour comparer les plans.

EXPLAIN Plans

Affiche le plan estimé d'une requête sans l'exécuter.

EXPLAIN ANALYZE Plans

Exécute la requête et affiche le plan avec les temps et lignes réels.

GIN Index

Index inversé qui recense, pour chaque élément, les lignes qui le contiennent.

Hash Join Accès & jointures

Jointure qui charge une table en mémoire sous forme de table de hachage.

Index composite Index

Index sur plusieurs colonnes, utilisable si la requête filtre sur la première.

Index couvrant (INCLUDE) Index

Index qui embarque des colonnes supplémentaires pour éviter de lire la table.

Index Only Scan Accès & jointures

Réponse fournie par l'index seul, sans lire la table.

Index partiel Index

Index limité aux lignes vérifiant une condition.

Index redondant Maintenance

Index rendu inutile par un autre qui commence par les mêmes colonnes.

Index Scan Accès & jointures

Parcours d'un index suivi de la lecture de chaque ligne dans la table.

Index sur expression Index

Index sur le résultat d'un calcul, utilisé si la requête contient la même expression.

Merge Join Accès & jointures

Jointure qui parcourt en parallèle deux entrées déjà triées.

Nested Loop Accès & jointures

Jointure qui cherche, pour chaque ligne de gauche, ses correspondances à droite.

Pagination par clé (keyset) Optimisation

Pagination qui repart du dernier identifiant affiché au lieu d'utiliser OFFSET.

Parallélisme (Gather) Plans

Répartition d'une lecture entre plusieurs processus, rassemblés par le nœud Gather.

pg_stat_statements Maintenance

Extension qui cumule les appels et le temps d'exécution de chaque requête.

pg_trgm Index

Extension qui découpe le texte en trigrammes : recherche « contient » et tolérance aux fautes.

Plan d'exécution Plans

Suite d'opérations choisie par PostgreSQL pour exécuter une requête.

Planificateur Plans

Composant qui évalue les stratégies possibles et choisit la moins coûteuse.

Seq Scan Accès & jointures

Lecture complète d'une table, bloc après bloc.

Statistiques (pg_stats) Accès & jointures

Informations sur la distribution des valeurs, utilisées pour estimer les lignes.

Sélectivité Accès & jointures

Proportion de lignes retenues par une condition ; plus elle est faible, plus l'index est utile.

VACUUM Maintenance

Opération qui récupère l'espace des lignes mortes et met à jour la carte de visibilité.
