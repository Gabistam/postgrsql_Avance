🔐N34  Les transactions : tout ou rien
Transactions

🎯 À quoi ça sert

Une transaction regroupe plusieurs instructions en une seule unité : soit toutes sont validées (COMMIT), soit aucune (ROLLBACK). C'est ce qui empêche un virement de débiter un compte sans créditer l'autre. Vous l'avez déjà vu à l'œuvre : un CALL (N27) est une transaction. Ici, c'est vous qui en fixez les limites.

💡 Analogie — un panier en ligne : vous ajoutez, retirez, modifiez librement ; rien n'est acheté tant que vous n'avez pas cliqué sur « Payer » (COMMIT). Fermer l'onglet (ROLLBACK) et tout disparaît, comme si de rien n'était.

🧩 Syntaxe

Propriété ACIDGarantie
AtomicitéTout ou rien : une transaction interrompue ne laisse aucune trace
CohérenceLes contraintes (clés, CHECK) sont respectées à la validation
IsolationLes transactions simultanées ne se perturbent pas (N35)
DurabilitéUne fois validée, une modification survit à une panne
SQL
BEGIN;                          -- ouvre une transaction
  ...
COMMIT;                         -- valide tout        |  ROLLBACK;  -- annule tout

SAVEPOINT nom;                  -- point de reprise à l'intérieur d'une transaction
ROLLBACK TO SAVEPOINT nom;      -- revient à ce point, sans tout annuler

-- Sans BEGIN, chaque instruction est sa propre transaction (mode « autocommit »)

👁️N35  Isolation : ce que voit une transaction
Transactions

🎯 À quoi ça sert

Quand plusieurs transactions s'exécutent en même temps, que voit chacune des modifications des autres ? PostgreSQL utilise le MVCC (Multi-Version Concurrency Control) : chaque modification crée une nouvelle version de la ligne, et chaque transaction lit la version qui correspond à son instantané. Résultat : les lectures ne bloquent jamais les écritures, et inversement. Le niveau d'isolation décide quand cet instantané est pris.

💡 Analogie — deux personnes consultent un tableau d'affichage. En READ COMMITTED, chacune regarde le tableau en direct à chaque coup d'œil. En REPEATABLE READ, chacune a pris une photo au début et ne regarde plus que sa photo. En SERIALIZABLE, un arbitre vérifie en plus qu'aucune décision n'a été prise sur une photo devenue fausse.

🧩 Syntaxe

NiveauInstantané pris…Ce qui peut arriver
READ COMMITTEDà chaque instruction (par défaut)Deux lectures identiques dans la même transaction peuvent donner des résultats différents
REPEATABLE READau début de la transactionLectures stables ; une mise à jour concurrente d'une même ligne fait échouer la transaction
SERIALIZABLEau début, avec contrôle des dépendancesRésultat identique à une exécution l'une après l'autre ; certaines transactions échouent et doivent être relancées
SQL
BEGIN ISOLATION LEVEL REPEATABLE READ;   -- ou READ COMMITTED, SERIALIZABLE
  ...
COMMIT;

⚠️ Piège fréquent

Croire qu'une transaction suffit à tout protéger. En READ COMMITTED ou en REPEATABLE READ, l'exemple des gardes aurait laissé la cité sans aucun garde : chaque transaction était correcte isolément. Ce phénomène (write skew) n'est empêché que par SERIALIZABLE, ou par un verrou explicite (N36). En contrepartie, SERIALIZABLE et REPEATABLE READ exigent que l'application sache relancer une transaction refusée.
🔒N36  Verrous : les mises à jour perdues
Concurrence

🎯 À quoi ça sert

Le scénario le plus courant en production : deux traitements lisent la même valeur, calculent chacun de leur côté, puis écrivent. Le second écrase le premier : c'est une mise à jour perdue. Aucune erreur, aucun message, juste des données fausses. Trois parades : écrire le calcul dans l'UPDATE lui-même, verrouiller la ligne lue avec FOR UPDATE, ou sauter les lignes déjà prises avec SKIP LOCKED.

💡 Analogie — deux personnes éditent le même document partagé hors connexion ; la dernière qui synchronise écrase le travail de l'autre. Le verrou, c'est le panneau « en cours de modification par… » qui fait patienter la seconde.

🧩 Syntaxe

SQL
-- 1. Calcul atomique : la lecture et l'écriture ne font qu'un
UPDATE comptes SET solde = solde - 100 WHERE id = 1;

-- 2. Verrou de ligne : les autres FOR UPDATE attendent jusqu'au COMMIT
SELECT solde FROM comptes WHERE id = 1 FOR UPDATE;

-- 3. File de travail : prendre la première ligne libre, sans attendre
SELECT id FROM taches WHERE statut = 'a_faire' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;

-- Ne pas attendre du tout (NOWAIT), ou pas plus d'un délai
SELECT … FOR UPDATE NOWAIT;
SET lock_timeout = '2s';

💀N37  Les interblocages (deadlocks)
Concurrence

🎯 À quoi ça sert

Un interblocage survient quand deux transactions s'attendent mutuellement : A tient la ligne 1 et veut la 2, B tient la 2 et veut la 1. Aucune ne peut avancer. PostgreSQL le détecte (après deadlock_timeout, 1 seconde par défaut) et annule l'une des deux pour débloquer l'autre.

💡 Analogie — deux voitures face à face dans une ruelle, chacune attendant que l'autre recule. Il faut qu'un agent en fasse reculer une. La prévention : un sens de circulation unique, que tout le monde respecte.

🧩 Syntaxe

SQL
-- Prévention : toujours verrouiller dans le même ordre, quel que soit le sens de l'opération
SELECT … FROM comptes WHERE id IN (:a, :b) ORDER BY id FOR UPDATE;

⚠️ Piège fréquent

Traiter l'interblocage comme un bug rare qu'on ignore. Sur une application chargée, il arrive régulièrement. Deux règles : verrouiller toujours dans le même ordre (par identifiant croissant, par exemple), et prévoir côté application une relance automatique des transactions annulées (erreurs 40P01 pour un interblocage, 40001 pour un échec de sérialisation). La procédure de N40 applique la première règle.

🚦 Point d'étape

Les transactions garantissent le tout ou rien, l'isolation règle ce que chacun voit, les verrous empêchent les écrasements, et l'ordre de verrouillage évite les interblocages. Reste une autre question : qui a le droit de faire quoi dans la base ?

🪪N38  Rôles et privilèges : le moindre privilège
Sécurité

🎯 À quoi ça sert

Dans PostgreSQL, tout accès passe par un rôle. Un rôle peut se connecter (un utilisateur) ou servir de groupe de droits. Le principe du moindre privilège : chaque rôle ne reçoit que les droits dont il a strictement besoin. Si l'application est compromise, l'attaquant ne peut faire que ce que l'application pouvait faire.

💡 Analogie — les badges d'un immeuble de bureaux : le prestataire de ménage ouvre tous les étages mais pas la salle des serveurs ; le stagiaire ouvre son étage ; seul l'administrateur a le passe-partout. On ne donne pas le passe-partout au livreur « pour être tranquille ».

🧩 Syntaxe

SQL
CREATE ROLE groupe NOLOGIN;                         -- un groupe de droits
CREATE ROLE utilisateur LOGIN PASSWORD '…';         -- un compte de connexion
GRANT groupe TO utilisateur;                        -- l'utilisateur hérite des droits du groupe

GRANT SELECT, INSERT, UPDATE ON table TO groupe;    -- donner des droits
REVOKE DELETE ON table FROM groupe;                 -- les retirer

SET ROLE utilisateur;   …   RESET ROLE;            -- tester avec l'identité d'un autre rôle

🔑 Et les mots de passe des joueurs ?

Les rôles PostgreSQL protègent l'accès à la base. Les mots de passe des utilisateurs de l'application sont un autre sujet : on ne les stocke jamais en clair, mais sous forme d'empreinte calculée avec un algorithme lent et salé (bcrypt, Argon2). C'est normalement le travail de l'application (password_hash() en PHP, bcrypt en Node.js…). L'extension pgcrypto permet de le faire en SQL :

SQL
CREATE EXTENSION IF NOT EXISTS pgcrypto;
SQL
WITH compte AS (
    SELECT crypt('Tr0ub4dor&3', gen_salt('bf')) AS empreinte   -- bcrypt, sel aléatoire
)
SELECT LEFT(empreinte, 7)                     AS algorithme,
       crypt('Tr0ub4dor&3', empreinte) = empreinte AS bon_mot_de_passe,
       crypt('tr0ub4dor&3', empreinte) = empreinte AS mauvais_mot_de_passe
FROM compte;
▶ Résultat 1 ligne

L'empreinte change à chaque calcul (sel aléatoire) ; on vérifie un mot de passe en recalculant l'empreinte avec le même sel.

⚠️ Piège fréquent

Faire tourner l'application avec le compte postgres (ou tout superutilisateur). Il ignore tous les droits et toutes les politiques de sécurité (N39) : la moindre injection SQL (N41) donne alors un accès total, jusqu'à la suppression de la base. L'application a son propre rôle, sans droit sur la structure (CREATE, DROP, ALTER) ; les migrations passent par un autre compte.
🧱N39  Row Level Security : chacun ses lignes
Sécurité

🎯 À quoi ça sert

Les privilèges (N38) portent sur des tables entières : l'application lit tous les messages. La Row Level Security (RLS) filtre ligne par ligne : chaque aventurier ne voit que les messages qu'il a envoyés ou reçus, même si l'application oublie le WHERE, même si une requête est piégée. La règle est appliquée par la base, dans toutes les requêtes.

💡 Analogie — une boîte aux lettres collective : tout le monde a accès au hall (le privilège sur la table), mais chaque clé n'ouvre que sa propre boîte (la politique RLS).

🧩 Syntaxe

SQL
ALTER TABLE t ENABLE ROW LEVEL SECURITY;           -- active la RLS : sans politique, plus rien n'est visible

CREATE POLICY nom ON t
  FOR SELECT                                       -- ou INSERT, UPDATE, DELETE, ALL
  USING (condition);                               -- lignes visibles / modifiables

CREATE POLICY nom ON t
  FOR INSERT
  WITH CHECK (condition);                          -- lignes que l'on a le droit d'écrire

-- L'application indique qui est connecté, pour la session (ou SET LOCAL pour la transaction)
SET app.aventurier_id = '1';
current_setting('app.aventurier_id', true)         -- true : NULL si le paramètre n'existe pas
NULLIF(current_setting('app.aventurier_id', true), '')  -- '' après un RESET : on le ramène à NULL

🔬 Exemple commenté

SQL
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;

CREATE POLICY messages_lecture ON messages
  FOR SELECT
  USING (NULLIF(current_setting('app.aventurier_id', true), '')::INTEGER IN (expediteur_id, destinataire_id));

CREATE POLICY messages_envoi ON messages
  FOR INSERT
  WITH CHECK (expediteur_id = NULLIF(current_setting('app.aventurier_id', true), '')::INTEGER);

🎫N40  SECURITY DEFINER : une porte contrôlée
Sécurité

🎯 À quoi ça sert

L'application ne peut pas modifier les pièces (N38) : tant mieux. Mais comment réaliser un virement entre joueurs ? En lui donnant accès à une procédure qui, elle, a le droit de modifier les pièces, et qui applique toutes les vérifications. Avec SECURITY DEFINER, une fonction ou une procédure s'exécute avec les droits de son propriétaire, et non de l'appelant.

💡 Analogie — le guichet d'une banque : le client n'entre pas dans la salle des coffres, mais le guichetier, qui y a accès, effectue l'opération pour lui après avoir vérifié la demande.

🧩 Syntaxe

SQL
CREATE PROCEDURE p(…)
LANGUAGE plpgsql
SECURITY DEFINER                       -- s'exécute avec les droits du propriétaire
SET search_path = public, pg_temp      -- indispensable : chemin de recherche figé
AS $$ … $$;

REVOKE EXECUTE ON PROCEDURE p(…) FROM PUBLIC;   -- par défaut, tout le monde peut l'exécuter
GRANT  EXECUTE ON PROCEDURE p(…) TO groupe;

🔬 Exemple commenté

SQL
CREATE PROCEDURE transferer(p_de TEXT, p_vers TEXT, p_montant INTEGER)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
    v_solde INTEGER;
BEGIN
    IF p_montant <= 0 THEN
        RAISE EXCEPTION 'Montant invalide : %', p_montant;
    END IF;

    -- Verrouiller les deux comptes, toujours dans le même ordre (N36, N37)
    PERFORM 1 FROM aventuriers WHERE pseudo IN (p_de, p_vers) ORDER BY id FOR UPDATE;

    SELECT pieces INTO v_solde FROM aventuriers WHERE pseudo = p_de;
    IF NOT FOUND THEN RAISE EXCEPTION 'Expéditeur inconnu : %', p_de; END IF;
    IF v_solde < p_montant THEN
        RAISE EXCEPTION 'Fonds insuffisants : % pièces pour un virement de %', v_solde, p_montant;
    END IF;

    UPDATE aventuriers SET pieces = pieces - p_montant WHERE pseudo = p_de;
    UPDATE aventuriers SET pieces = pieces + p_montant WHERE pseudo = p_vers;
    IF NOT FOUND THEN RAISE EXCEPTION 'Destinataire inconnu : %', p_vers; END IF;
END;
$$;

REVOKE EXECUTE ON PROCEDURE transferer(TEXT, TEXT, INTEGER) FROM PUBLIC;
GRANT  EXECUTE ON PROCEDURE transferer(TEXT, TEXT, INTEGER) TO jeu_ecriture;

⚠️ Piège fréquent

Oublier SET search_path. Une fonction SECURITY DEFINER qui écrit aventuriers sans préciser le schéma cherche cette table dans le search_path de l'appelant. Un utilisateur malveillant peut y placer un schéma (ou une table temporaire) contenant un faux objet du même nom, et détourner la fonction avec les droits de son propriétaire. Figer le chemin (public, pg_temp, avec pg_temp en dernier) supprime ce risque. Pensez aussi au REVOKE … FROM PUBLIC : sans lui, n'importe quel rôle peut exécuter la procédure.
💉N41  L'injection SQL et les requêtes paramétrées
Sécurité

🎯 À quoi ça sert

L'injection SQL reste l'une des failles les plus exploitées sur le web. Elle survient quand une requête est construite en collant du texte fourni par l'utilisateur : ce texte peut alors modifier la requête elle-même. La parade est simple et absolue : ne jamais concaténer une valeur dans du SQL, mais la transmettre comme paramètre, séparée du code.

💡 Analogie — un formulaire de virement où le client écrirait lui-même la phrase entière : « Virer 10 € à Paul ». Un malin écrit : « Virer 10 € à Paul, puis vider le compte ». Le formulaire à cases (montant, bénéficiaire) interdit cette ruse : une case ne contient qu'une valeur, jamais une instruction.

🧩 Syntaxe

SQL
-- En PL/pgSQL : SQL statique (paramètres automatiques)…
RETURN QUERY SELECT … FROM t WHERE col = p_valeur;

-- …ou SQL dynamique avec USING (valeurs) et format (identifiants)
RETURN QUERY EXECUTE format('SELECT … FROM %I WHERE col = $1', p_table) USING p_valeur;

-- Requête préparée : le texte et les valeurs voyagent séparément
PREPARE nom(TEXT) AS SELECT … WHERE col = $1;
EXECUTE nom('valeur');

🔬 Exemple commenté

Croire qu'échapper les apostrophes « à la main » ou filtrer quelques mots-clés suffit : il existe toujours un contournement. Et même avec des requêtes paramétrées, le moindre privilège (N38) et la RLS (N39) restent indispensables : c'est la défense en profondeur.
