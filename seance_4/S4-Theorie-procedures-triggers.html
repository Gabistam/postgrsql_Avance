📜N26  Les procédures stockées : CREATE PROCEDURE et CALL
Procédures

🎯 À quoi ça sert

Une procédure enregistre dans la base une opération métier complète : acheter un objet, valider une commande, clôturer un mois. Comme une fonction (N17), elle s'écrit en PL/pgSQL ; mais elle est faite pour agir plutôt que pour calculer une valeur, et elle peut piloter la transaction (N28).

💡 Analogie — la fonction est une calculatrice : on lui donne des nombres, elle renvoie un résultat. La procédure est un guichetier : on lui confie une démarche, il enchaîne toutes les étapes (vérifier, débiter, enregistrer) et vous dit si c'est fait.

🧩 Syntaxe

Fonction (N16, N17)Procédure
AppelSELECT f(…)CALL p(…)
Utilisable dans une requêteOui (SELECT, WHERE…)Non, uniquement par CALL
Valeur de retourOui (RETURNS)Non, mais des paramètres INOUT
COMMIT / ROLLBACK à l'intérieurInterditAutorisé (N28)
Usage typiqueCalculer, transformerEnchaîner des écritures métier
SQL
CREATE [OR REPLACE] PROCEDURE nom(p_param TYPE, INOUT p_resultat TYPE DEFAULT NULL)
LANGUAGE plpgsql
AS $$
DECLARE
    v_ligne  une_table%ROWTYPE;      -- variable qui a la structure d'une ligne de la table
BEGIN
    ...
END;
$$;

CALL nom(valeur);

🔬 Exemple commenté

Une première procédure simple : créditer des pièces d'or à un aventurier.

SQL
CREATE PROCEDURE crediter(p_pseudo TEXT, p_montant INTEGER)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE aventuriers SET pieces = pieces + p_montant WHERE pseudo = p_pseudo;
    IF NOT FOUND THEN                          -- aucune ligne modifiée
        RAISE EXCEPTION 'Aventurier inconnu : %', p_pseudo;
    END IF;
END;
$$;
SQL
CALL crediter('kairo', 50);
SELECT pseudo, pieces FROM aventuriers WHERE pseudo = 'kairo';

Une vraie opération métier : l'achat d'un objet. Six étapes qui doivent réussir ensemble. Le paramètre INOUT renvoie le prix payé.

SQL
CREATE PROCEDURE acheter(p_pseudo TEXT, p_objet TEXT, p_quantite INTEGER DEFAULT 1,
                         INOUT p_total INTEGER DEFAULT NULL)
LANGUAGE plpgsql
AS $$
DECLARE
    v_av   aventuriers%ROWTYPE;
    v_obj  objets%ROWTYPE;
BEGIN
    -- 1. L'aventurier et l'objet existent-ils ?
    SELECT * INTO v_av FROM aventuriers WHERE pseudo = p_pseudo;
    IF NOT FOUND THEN RAISE EXCEPTION 'Aventurier inconnu : %', p_pseudo; END IF;
    SELECT * INTO v_obj FROM objets WHERE nom = p_objet;
    IF NOT FOUND THEN RAISE EXCEPTION 'Objet inconnu : %', p_objet; END IF;

    -- 2. Stock suffisant ?
    IF v_obj.stock < p_quantite THEN
        RAISE EXCEPTION 'Stock insuffisant pour « % » : % disponible(s)', p_objet, v_obj.stock;
    END IF;

    -- 3. Fonds suffisants ?
    p_total := v_obj.prix * p_quantite;
    IF v_av.pieces < p_total THEN
        RAISE EXCEPTION 'Fonds insuffisants : % pièces pour un achat de %', v_av.pieces, p_total
              USING HINT = 'Terminez des quêtes pour gagner des pièces.';
    END IF;

    -- 4. Mouvements : stock, pièces, inventaire, historique
    UPDATE objets      SET stock  = stock  - p_quantite WHERE id = v_obj.id;
    UPDATE aventuriers SET pieces = pieces - p_total    WHERE id = v_av.id;
    INSERT INTO inventaire (aventurier_id, objet_id, quantite)
    VALUES (v_av.id, v_obj.id, p_quantite)
    ON CONFLICT (aventurier_id, objet_id)
        DO UPDATE SET quantite = inventaire.quantite + EXCLUDED.quantite;
    INSERT INTO achats (aventurier_id, objet_id, quantite, prix_total)
    VALUES (v_av.id, v_obj.id, p_quantite, p_total);
END;
$$;

⚠️ Piège fréquent

Écrire une procédure qui renvoie un résultat avec RETURN valeur; : c'est interdit, une procédure ne renvoie rien. Utilisez un paramètre INOUT, ou une fonction si l'objectif est de calculer. Autre confusion fréquente : SELECT acheter(…) au lieu de CALL acheter(…), qui provoque l'erreur acheter(…) is a procedure.
🛡️N27  Gérer les erreurs : RAISE et EXCEPTION
Procédures

🎯 À quoi ça sert

Une opération métier doit échouer proprement : avec un message compréhensible, et sans laisser la base à moitié modifiée. PL/pgSQL offre deux outils : RAISE pour signaler (information ou erreur), et le bloc EXCEPTION pour intercepter une erreur et réagir.

💡 Analogie — un distributeur de billets : si le solde est insuffisant, il refuse avec un message clair (RAISE EXCEPTION) et ne débite rien. S'il manque de billets en cours d'opération, il annule tout et rend la carte : on ne ressort jamais débité sans ses billets.

🧩 Syntaxe

SQL
RAISE NOTICE  'Information : %', valeur;            -- message, l'exécution continue
RAISE WARNING 'Attention : %', valeur;              -- avertissement, l'exécution continue
RAISE EXCEPTION 'Erreur : %', valeur                -- stoppe et annule
      USING HINT = 'Conseil pour corriger', ERRCODE = 'P0001';

BEGIN
    ...                                             -- instructions protégées
EXCEPTION
    WHEN unique_violation THEN ...                  -- erreur précise
    WHEN check_violation  THEN ...
    WHEN OTHERS THEN ...                            -- toute autre erreur (SQLSTATE, SQLERRM)
END;

DO $$ BEGIN ... END $$;                             -- bloc anonyme, pour tester sans créer de procédure

🔬 Exemple commenté

Une erreur métier. Kenji veut une épée à 150 pièces ; il n'en a que 45 :

SQL
CALL acheter('kenji', 'Épée courte');

HINT:  Terminez des quêtes pour gagner des pièces.

Tout ou rien. Même quand l'erreur survient après une première modification, tout est annulé. Ce bloc retire un arc du stock, puis tente de débiter 10 000 pièces à Kairo, ce que la contrainte CHECK (pieces >= 0) refuse :

END $$;
✖ Erreur PostgreSQL

DETAIL:  Failing row contains (7, kairo, 1, -9850, 0).

Intercepter une erreur. Une procédure d'inscription qui transforme un pseudo déjà pris en simple message :

SQL
CREATE PROCEDURE inscrire(p_pseudo TEXT)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO aventuriers (pseudo) VALUES (p_pseudo);
    RAISE NOTICE 'Bienvenue, % ! 100 pièces offertes.', p_pseudo;
EXCEPTION
    WHEN unique_violation THEN
        RAISE NOTICE 'Le pseudo « % » est déjà pris.', p_pseudo;
END;
$$;
SQL
CALL inscrire('sara');
CALL inscrire('Pixel');
💬 Messages
NOTICE:  Le pseudo « sara » est déjà pris.
NOTICE:  Bienvenue, Pixel ! 100 pièces offertes.
📌 Un bloc avec EXCEPTION crée un point de reprise : en cas d'erreur, seules les modifications faites dans ce bloc sont annulées, puis le code du WHEN s'exécute. C'est pratique, mais plus coûteux qu'un bloc simple : n'en mettez pas dans une boucle de milliers d'itérations sans raison.

⚠️ Piège fréquent

Le WHEN OTHERS THEN RAISE NOTICE … qui avale toutes les erreurs. La procédure « réussit », l'appelant croit que tout s'est bien passé, et les données sont incomplètes sans que personne ne le sache. N'interceptez que les erreurs que vous savez traiter ; pour les autres, laissez-les remonter, ou relancez-les avec RAISE; après avoir journalisé.
📦N28  Valider par lots : COMMIT dans une procédure
Procédures

🎯 À quoi ça sert

Par défaut, tout ce que fait un CALL est validé ou annulé d'un bloc. Pour un traitement très long (recalculer un million de lignes, purger des années d'historique), ce « tout ou rien » devient un problème : verrous tenus pendant des minutes, et tout le travail perdu à la moindre erreur. Une procédure peut alors valider par lots avec COMMIT. C'est ce qu'une fonction ne peut pas faire.

💡 Analogie — déménager un appartement. Tout charger dans un seul camion (une seule transaction) : si le camion tombe en panne, tout est bloqué. Faire des allers-retours (des lots validés) : chaque voyage terminé est acquis, et une panne ne fait perdre que le voyage en cours.

🧩 Syntaxe

SQL
CREATE PROCEDURE traitement_par_lots(p_lot INTEGER)
LANGUAGE plpgsql
AS $$
DECLARE
    v_compteur INTEGER := 0;
BEGIN
    FOR r IN SELECT id FROM une_table ORDER BY id LOOP
        UPDATE une_table SET ... WHERE id = r.id;
        v_compteur := v_compteur + 1;
        IF v_compteur % p_lot = 0 THEN
            COMMIT;                          -- valide le lot en cours
        END IF;
    END LOOP;
    COMMIT;                                  -- valide le dernier lot incomplet
END;
$$;

🔬 Exemple commenté

Distribuer un bonus de pièces à tous les aventuriers, en validant par lots de 3 :

SQL
CREATE PROCEDURE distribuer_bonus(p_montant INTEGER, p_lot INTEGER)
LANGUAGE plpgsql
AS $$
DECLARE
    r          RECORD;
    v_compteur INTEGER := 0;
BEGIN
    FOR r IN SELECT id FROM aventuriers ORDER BY id LOOP
        UPDATE aventuriers SET pieces = pieces + p_montant WHERE id = r.id;
        v_compteur := v_compteur + 1;
        IF v_compteur % p_lot = 0 THEN
            COMMIT;
            RAISE NOTICE 'Lot validé : % aventuriers traités', v_compteur;
        END IF;
    END LOOP;
    COMMIT;
    RAISE NOTICE 'Terminé : % aventuriers au total', v_compteur;
END;
$$;
SQL
CALL distribuer_bonus(10, 3);
💬 Messages
NOTICE:  Lot validé : 3 aventuriers traités
NOTICE:  Lot validé : 6 aventuriers traités
NOTICE:  Lot validé : 9 aventuriers traités
NOTICE:  Terminé : 9 aventuriers au total
Si une erreur survenait au 8e aventurier, les 6 premiers garderaient leur bonus : les deux premiers lots sont déjà validés.

Sur 9 aventuriers, c'est symbolique. Sur des millions de lignes, les lots raccourcissent la durée des verrous, limitent le volume à annuler en cas d'échec et permettent de reprendre là où le traitement s'est arrêté.

⚠️ Piège fréquent

Une procédure qui contient un COMMIT ne peut pas être appelée à l'intérieur d'une transaction ouverte par l'appelant : elle ne peut pas valider un travail qui ne lui appartient pas.
SQL
BEGIN;
CALL distribuer_bonus(10, 3);
ROLLBACK;
✖ Erreur PostgreSQL
ERROR:  invalid transaction termination
Même règle si l'appel vient d'une fonction, ou si le COMMIT se trouve dans un bloc qui possède une clause EXCEPTION. Ce mode de validation par lots est réservé aux traitements lancés seuls, par exemple depuis une tâche planifiée.

🚦 Point d'étape

Les procédures encapsulent les opérations métier, et leurs erreurs sont propres et annulent tout. Mais elles ne s'exécutent que si l'on pense à les appeler. La partie 2 présente le mécanisme qui s'exécute tout seul, à chaque modification : le trigger.

⚡N29  Anatomie d'un trigger
Triggers

🎯 À quoi ça sert

Un trigger (déclencheur) exécute automatiquement une fonction quand une table est modifiée : avant ou après un INSERT, un UPDATE ou un DELETE. Aucune application ne peut l'oublier ni le contourner : la règle est appliquée par la base elle-même, quel que soit le programme qui écrit.

💡 Analogie — un détecteur de mouvement : on ne l'appelle jamais, il se déclenche quand quelqu'un passe. BEFORE, c'est le portique qui peut refuser l'entrée ou vous faire vider vos poches ; AFTER, c'est la caméra qui enregistre votre passage.

🧩 Syntaxe

SQL
-- 1. La fonction trigger : sans paramètre, RETURNS TRIGGER
CREATE OR REPLACE FUNCTION trg_nom()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- NEW : la ligne après modification (INSERT, UPDATE)
    -- OLD : la ligne avant modification (UPDATE, DELETE)
    RETURN NEW;       -- BEFORE : la ligne à écrire (NULL = annuler l'écriture)
END;
$$;

-- 2. Le trigger : quand appeler la fonction
CREATE TRIGGER nom_trigger
{BEFORE | AFTER} {INSERT | UPDATE [OF colonne] | DELETE} [OR …] ON table
FOR EACH {ROW | STATEMENT}
[WHEN (condition)]
EXECUTE FUNCTION trg_nom();
VariableContenu
NEWLa nouvelle version de la ligne (INSERT, UPDATE)
OLDL'ancienne version de la ligne (UPDATE, DELETE)
TG_OPL'opération : 'INSERT', 'UPDATE' ou 'DELETE'
TG_TABLE_NAMELe nom de la table concernée
TG_WHEN'BEFORE' ou 'AFTER'

🔬 Exemple commenté

Des pseudos toujours propres, quelle que soit l'application qui les saisit : sans espaces superflus et en minuscules.

SQL
CREATE FUNCTION trg_normaliser_pseudo()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.pseudo := LOWER(TRIM(NEW.pseudo));    -- on corrige la ligne avant son écriture
    RETURN NEW;
END;
$$;

CREATE TRIGGER normaliser_pseudo
BEFORE INSERT OR UPDATE OF pseudo ON aventuriers
FOR EACH ROW
EXECUTE FUNCTION trg_normaliser_pseudo();
SQL
INSERT INTO aventuriers (pseudo) VALUES ('  DarkSasuke  ');
UPDATE aventuriers SET pseudo = pseudo WHERE pseudo = 'Pixel';      -- inscrit en N27
SELECT id, pseudo FROM aventuriers WHERE id >= 9 ORDER BY id;
▶ Résultat 2 lignes
idpseudo
10pixel
11darksasuke
« Pixel », inscrit avant le trigger, est corrigé à la première mise à jour de son pseudo. L'identifiant 9 n'apparaît pas : il a été consommé par l'inscription refusée de « sara » en N27. Une séquence ne revient jamais en arrière, même après une erreur.

⚠️ Piège fréquent

Dans un trigger BEFORE … FOR EACH ROW, RETURN NULL annule silencieusement l'écriture de la ligne : aucune erreur, juste une ligne qui n'arrive jamais.
SQL
CREATE TABLE test_trigger (x INTEGER);
CREATE FUNCTION trg_oubli() RETURNS TRIGGER LANGUAGE plpgsql
AS $$ BEGIN RETURN NULL; END; $$;              -- au lieu de RETURN NEW
CREATE TRIGGER oubli BEFORE INSERT ON test_trigger
FOR EACH ROW EXECUTE FUNCTION trg_oubli();
SQL
INSERT INTO test_trigger VALUES (1), (2), (3);
SELECT COUNT(*) AS lignes FROM test_trigger;
▶ Résultat 1 ligne
lignes
0
3 lignes insérées, 0 enregistrée, aucun message d'erreur.
SQL
DROP TABLE test_trigger; DROP FUNCTION trg_oubli();
C'est parfois voulu (ignorer une ligne), mais c'est le plus souvent un oubli. Dans un trigger BEFORE, terminez par RETURN NEW (ou RETURN OLD pour un DELETE).
🚧N30  Triggers BEFORE : compléter et valider
Triggers

🎯 À quoi ça sert

Un trigger BEFORE intervient avant l'écriture : il peut modifier la ligne (horodatage, valeur calculée) ou la refuser avec un message métier. C'est l'endroit des règles qu'une simple contrainte CHECK ne sait pas exprimer, parce qu'elles comparent l'ancienne et la nouvelle valeur.

💡 Analogie — le contrôle qualité en bout de chaîne : il appose la date de fabrication sur chaque produit et écarte ceux qui ne respectent pas les règles, avant la mise en rayon.

🧩 Syntaxe

SQL
CREATE FUNCTION trg_regles()
RETURNS TRIGGER LANGUAGE plpgsql
AS $$
BEGIN
    NEW.maj_le := now();                              -- compléter
    IF NEW.valeur > OLD.valeur * 2 THEN               -- valider (UPDATE)
        RAISE EXCEPTION 'Règle métier non respectée';
    END IF;
    RETURN NEW;
END;
$$;

🔬 Exemple commenté

Pour les objets de la boutique : dater chaque modification, et interdire une hausse de prix de plus de 50 % d'un coup (protection contre une faute de frappe).

SQL
CREATE FUNCTION trg_maj_objet()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'UPDATE' AND NEW.prix > OLD.prix * 1.5 THEN
        RAISE EXCEPTION 'Hausse de prix trop forte pour « % » : % → % (maximum +50 %%)',
              NEW.nom, OLD.prix, NEW.prix;
    END IF;
    NEW.maj_le := now();
    RETURN NEW;
END;
$$;

CREATE TRIGGER maj_objet
BEFORE INSERT OR UPDATE ON objets
FOR EACH ROW
EXECUTE FUNCTION trg_maj_objet();

FROM objets WHERE nom = 'Potion de soin';

Une faute de frappe (1 500 au lieu de 150) est bloquée avec un message explicite :

SQL

📌 Contrainte ou trigger ? Une règle qui ne dépend que de la ligne (prix > 0) s'écrit en CHECK : plus simple, plus rapide, visible dans \d. Le trigger est réservé aux règles qui comparent avant/après, consultent d'autres tables ou complètent la ligne.

⚠️ Piège fréquent

Dans une chaîne de format RAISE, le caractère % est réservé aux valeurs à insérer. Pour afficher un pourcentage, il faut le doubler (%%), sinon le message est faux ou provoque une erreur de nombre de paramètres. Autre piège : un trigger BEFORE UPDATE s'exécute même si la mise à jour ne change rien ; ajoutez WHEN (OLD IS DISTINCT FROM NEW) pour l'éviter.
🎥N31  Triggers AFTER : tracer et synchroniser
Automatisation

🎯 À quoi ça sert

Un trigger AFTER s'exécute une fois la modification faite : il ne peut plus changer la ligne, mais il peut agir ailleurs. Deux usages classiques : tenir un journal d'audit (qui a modifié quoi, avant/après) et maintenir une donnée dérivée (un total, un compteur) toujours à jour.

💡 Analogie — la boîte noire d'un avion : elle n'influence pas le vol, elle enregistre tout ce qui s'est passé, pour pouvoir le reconstituer ensuite.

🧩 Syntaxe

SQL
CREATE FUNCTION trg_audit()
RETURNS TRIGGER LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit (table_nom, operation, ancienne, nouvelle)
    VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(OLD), to_jsonb(NEW));   -- la ligne entière en JSONB (N13)
    RETURN NULL;                                                   -- ignoré pour un trigger AFTER
END;
$$;

Plutôt que de corriger chaque procédure (et d'en oublier une), un trigger sur inventaire recalcule le total à chaque changement. Un second trigger journalise toutes les modifications des aventuriers :

SQL
CREATE FUNCTION trg_nb_objets()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_id INTEGER := CASE WHEN TG_OP = 'DELETE' THEN OLD.aventurier_id ELSE NEW.aventurier_id END;
BEGIN
    UPDATE aventuriers
    SET nb_objets = COALESCE((SELECT SUM(quantite) FROM inventaire WHERE aventurier_id = v_id), 0)
    WHERE id = v_id;
    RETURN NULL;
END;
$$;

CREATE TRIGGER nb_objets
AFTER INSERT OR UPDATE OR DELETE ON inventaire
FOR EACH ROW
EXECUTE FUNCTION trg_nb_objets();

CREATE FUNCTION trg_audit()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit (table_nom, operation, ancienne, nouvelle)
    VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(OLD), to_jsonb(NEW));
    RETURN NULL;
END;
$$;

CREATE TRIGGER audit_aventuriers
AFTER INSERT OR UPDATE OR DELETE ON aventuriers
FOR EACH ROW
EXECUTE FUNCTION trg_audit();

🎚️N32  Triggers d'instruction, tables de transition et WHEN
Automatisation

🎯 À quoi ça sert

Un trigger FOR EACH ROW s'exécute une fois par ligne : un UPDATE de 10 000 lignes l'appelle 10 000 fois. Un trigger FOR EACH STATEMENT s'exécute une fois par instruction, et voit l'ensemble des lignes modifiées grâce aux tables de transition. La clause WHEN, elle, évite d'appeler la fonction quand ce n'est pas utile.

💡 Analogie — le facteur qui sonne pour chaque lettre (par ligne) ou qui dépose tout le courrier d'un coup avec un bordereau récapitulatif (par instruction).

🧩 Syntaxe

SQL
CREATE TRIGGER nom
AFTER UPDATE ON table
REFERENCING OLD TABLE AS avant NEW TABLE AS apres   -- tables de transition (AFTER uniquement)
FOR EACH STATEMENT
EXECUTE FUNCTION trg_resume();

CREATE TRIGGER nom
AFTER UPDATE OF colonne ON table
FOR EACH ROW
WHEN (OLD.colonne > 0 AND NEW.colonne = 0)           -- appelé seulement si la condition est vraie
EXECUTE FUNCTION trg_alerte();

🔬 Exemple commenté

Un résumé par instruction. Chaque changement de prix groupé est journalisé en une ligne : nombre d'objets concernés et variation moyenne.

SQL
CREATE FUNCTION trg_journal_prix()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO journal_prix (nb_objets, variation_moy)
    SELECT COUNT(*), ROUND(AVG(100.0 * (n.prix - o.prix) / o.prix), 2)
    FROM avant o
    JOIN apres n ON n.id = o.id
    WHERE n.prix <> o.prix                       -- seulement les prix réellement modifiés
    HAVING COUNT(*) > 0;                         -- rien à journaliser : aucune ligne
    RETURN NULL;
END;
$$;

CREATE TRIGGER journal_prix
AFTER UPDATE ON objets
REFERENCING OLD TABLE AS avant NEW TABLE AS apres
FOR EACH STATEMENT
EXECUTE FUNCTION trg_journal_prix();
SQL
UPDATE objets SET prix = ROUND(prix * 1.10) WHERE categorie IN ('potion', 'arme');
SELECT id, nb_objets, variation_moy FROM journal_prix;

    RETURN NULL;

$$;

⚠️ Piège fréquent

Les tables de transition ne sont disponibles qu'avec AFTER, et pas avec une liste de colonnes (UPDATE OF …). Et un trigger d'instruction se déclenche même si aucune ligne n'est modifiée : un UPDATE … WHERE qui ne trouve rien l'appelle quand même. D'où le HAVING COUNT(*) > 0 ci-dessus, sans lequel chaque achat (qui modifie un stock, pas un prix) ajouterait une ligne vide au journal.

🚦 Point d'étape

Normaliser, valider, dater, auditer, synchroniser, résumer, alerter : les triggers automatisent tout cela. Mais chaque trigger en ajoute un peu plus à chaque écriture, et ils s'enchaînent sans être visibles dans le code de l'application. La partie 3 apprend à les garder sous contrôle.

🧯N33  Maîtriser les triggers : cascades, boucles et arbitrages
Bonnes pratiques

🎯 À quoi ça sert

Les triggers sont puissants parce qu'ils sont invisibles : c'est aussi leur principal danger. Un développeur qui écrit un simple UPDATE ne voit pas les cinq triggers qu'il déclenche. Le tech lead doit savoir les inventorier, éviter les boucles, les suspendre pour un import massif, et décider ce qui relève de la base ou de l'application.

💡 Analogie — des dominos : pousser le premier est anodin ; savoir combien vont tomber, et s'il y en a un qui revient pousser le premier, demande d'avoir le plan de la chaîne sous les yeux.

🧩 Syntaxe

SQL
-- Inventaire des triggers
SELECT event_object_table, trigger_name, action_timing, event_manipulation
FROM information_schema.triggers;

-- Suspendre les triggers utilisateur d'une table (import massif, maintenance)
ALTER TABLE t DISABLE TRIGGER USER;
ALTER TABLE t ENABLE TRIGGER USER;

-- Profondeur d'imbrication courante (0 hors trigger)
SELECT pg_trigger_depth();

🔬 Exemple commenté

1. Inventorier. Tous les triggers posés pendant la séance :

SQL

       STRING_AGG(event_manipulation, ', ' ORDER BY event_manipulation) AS evenements
FROM information_schema.triggers
WHERE event_object_table IN ('aventuriers', 'objets', 'inventaire')
GROUP BY event_object_table, trigger_name, action_timing
ORDER BY table_cible, moment DESC, trigger_name;

Ce que déclenche un seul CALL acheter(…) :

Cascade
CALL acheter(…)
├── UPDATE objets (stock)
│   ├── BEFORE ROW   maj_objet         → date de modification
│   ├── AFTER  ROW   alerte_rupture    → seulement si le stock tombe à 0 (WHEN)
│   └── AFTER  STMT  journal_prix      → rien à journaliser (le prix n'a pas changé)
├── UPDATE aventuriers (pièces)
│   └── AFTER  ROW   audit_aventuriers → 1 ligne d'audit
├── INSERT/UPDATE inventaire
│   └── AFTER  ROW   nb_objets
│       └── UPDATE aventuriers (nb_objets)
│           └── AFTER ROW audit_aventuriers → 1 ligne d'audit de plus
└── INSERT achats

2. La boucle infinie. Un trigger AFTER UPDATE qui met à jour sa propre table se redéclenche lui-même :

SQL
CREATE FUNCTION trg_boucle() RETURNS TRIGGER LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE aventuriers SET niveau = NEW.niveau WHERE id = NEW.id;   -- relance le trigger…
    RETURN NULL;
END;
$$;
CREATE TRIGGER boucle AFTER UPDATE ON aventuriers
FOR EACH ROW EXECUTE FUNCTION trg_boucle();
SQL
UPDATE aventuriers SET niveau = niveau + 1 WHERE pseudo = 'kairo';
✖ Erreur PostgreSQL
ERROR:  stack depth limit exceeded
HINT:  Increase the configuration parameter "max_stack_depth" (currently 2048kB), after ensuring the platform's stack depth limit is adequate.
SQL
DROP TRIGGER boucle ON aventuriers;
DROP FUNCTION trg_boucle();

PostgreSQL finit par s'arrêter sur un dépassement de pile, et toute l'instruction est annulée. Deux remèdes : modifier NEW dans un trigger BEFORE plutôt que de relancer un UPDATE, ou, en dernier recours, sortir si pg_trigger_depth() > 1.

3. L'ordre d'exécution. Quand plusieurs triggers répondent au même événement, au même moment, PostgreSQL les exécute par ordre alphabétique de leur nom. Si l'ordre compte, nommez-les en conséquence (t10_normaliser, t20_valider…).

4. L'import massif. Pour charger un million de lignes déjà contrôlées, désactiver temporairement les triggers utilisateur évite un million d'appels :

SQL
ALTER TABLE inventaire DISABLE TRIGGER USER;
-- … chargement massif …
ALTER TABLE inventaire ENABLE TRIGGER USER;
-- puis recalculer une fois pour toutes les données dérivées (nb_objets)

⚠️ Piège fréquent

Tout mettre en triggers « pour être sûr ». Chaque trigger rend les écritures plus lentes et le comportement plus difficile à comprendre : un bug devient une enquête. Un trigger se justifie quand la règle doit être garantie quel que soit le programme qui écrit (audit, intégrité, normalisation). La logique métier qui dépend du contexte (envoyer un email, appeler une API, appliquer une promotion) reste dans l'application.
