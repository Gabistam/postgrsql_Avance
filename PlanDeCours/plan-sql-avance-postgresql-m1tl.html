🛒Fil rouge : ShopFlow

Une marketplace où plusieurs vendeurs publient des produits achetés par des clients. Le domaine est volontairement riche : hiérarchie de catégories (récursivité), stocks (triggers, transactions), paiements (atomicité), données multi-vendeurs (RLS) et assez de volume pour sentir la différence qu'apporte un bon index.

-- Schéma cible (fourni en S1)
vendeurs(id, nom, email, created_at)
clients(id, nom, email, ville, created_at)
categories(id, nom, parent_id)          -- arbre
produits(id, vendeur_id, categorie_id,
         nom, prix, stock, attributs JSONB)
commandes(id, client_id, statut, created_at)
lignes_commande(commande_id, produit_id,
                quantite, prix_unitaire)
paiements(id, commande_id, montant, statut)
audit_log(id, table_name, op, old, new, at)

  • PostgreSQL 16 ou 17 installé (postgresql.org) — ou via Docker postgres:17
  • Un client : psql + DBeaver ou pgAdmin
  • Extensions activables : pg_stat_statements, pg_trgm
  • Repo Git personnel shopflow-sql créé avant S1
  • Prérequis : SELECT / JOIN / GROUP BY maîtrisés
⚠️ À envoyer aux étudiants avant le 25/09 au matin : les 20 premières minutes de S1 ne suffisent pas à dépanner une installation Windows capricieuse.
🤖Usage de l'IA
  • Réécrire une requête complexe, puis prouver l'équivalence (mêmes résultats) et le gain (EXPLAIN ANALYZE)
  • Soumettre un plan d'exécution à l'IA pour repérer les goulets d'étranglement, puis vérifier chaque hypothèse par une mesure
  • Règle du module : toute requête produite avec l'IA est signalée dans le README du rendu
🌱Démarche RSE
  • Mesurer avant d'optimiser : buffers lus, temps d'exécution, volume scanné
  • Chaque optimisation du rapport S3 est traduite en charge serveur économisée
  • Sobriété : pas d'index « au cas où » (coût en écriture et en stockage), purge et archivage pensés dès la modélisation

CREATE OR REPLACE FUNCTION fn_ca_vendeur(p_vendeur INT, p_debut DATE, p_fin DATE)
RETURNS NUMERIC LANGUAGE plpgsql STABLE AS $$
DECLARE v_ca NUMERIC;
BEGIN
  IF p_debut > p_fin THEN
    RAISE EXCEPTION 'Période invalide : % > %', p_debut, p_fin;
  END IF;
  SELECT COALESCE(SUM(l.quantite * l.prix_unitaire), 0) INTO v_ca
  FROM lignes_commande l
  JOIN produits p ON p.id = l.produit_id
  JOIN commandes c ON c.id = l.commande_id
  WHERE p.vendeur_id = p_vendeur AND c.created_at::date BETWEEN p_debut AND p_fin;
  RETURN v_ca;
END; $$;
⚠️ Déclarer IMMUTABLE une fonction qui lit une table : ça compile, mais le planificateur peut mettre en cache un résultat faux. Montrez-le, c'est une erreur qui marque.

Exemples hors fil rouge : vue « fiche technique » d'un parc automobile d'occasion, vue matérialisée du classement d'un tournoi.

CREATE OR REPLACE FUNCTION trg_audit() RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log(table_name, op, old, new, at)
  VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(OLD), to_jsonb(NEW), now());
  RETURN NULL;  -- ignoré pour un trigger AFTER
END; $$;

CREATE TRIGGER audit_produits
AFTER INSERT OR UPDATE OR DELETE ON produits
FOR EACH ROW EXECUTE FUNCTION trg_audit();
⚠️ Pièges à montrer : trigger qui met à jour sa propre table (récursion), cascade de triggers invisible pour les développeurs, et coût d'un trigger ligne à ligne sur un import massif.

Exemples hors fil rouge : mise à jour automatique du classement d'une équipe après saisie d'un score de match, journal des modifications d'un dossier véhicule.

ALTER TABLE produits ENABLE ROW LEVEL SECURITY;

CREATE POLICY vendeur_ses_produits ON produits
